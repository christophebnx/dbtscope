## Chosen design

### 1. Shape of `cli.py`

One module (the CLI is not a package; `tests/unit/test_layering.py` needs no change). Sections, each one responsibility:

| Name | Owns |
|---|---|
| `PROG = "dbtscope"`, `HELP`, `EPILOG` | Program name, one-line description, examples |
| `app: typer.Typer` + `command(...)` | The interface: options, help panels, choices. The callback **does no work**: it returns an `Options` value (frozen dataclass of the 11 option values). |
| `Options` | The parsed command line (`project_dir`, `config`, `preset`, `output`, `view`, `manifest`, `no_parse`, `no_open`, `dbt`, `offline`) |
| `RunError(Exception)` | A run-level failure the CLI detects itself (paths, dbt, output, empty result). Message already in final form `<what>; <what to do>`. |
| `_resolve(options) -> Inputs` | The one place that resolves and checks every path given on the command line: project folder, `--config`, `--manifest`, `--output`, `--dbt` (§ 3). Raises `RunError`. |
| `_dbt_parse(dbt, project)` | Runs `dbt parse`, dbt's output on our stderr (§ 5), maps `OSError` and non-zero exit to `RunError`. |
| `_write_page(output, data)` | `mkdir` + `atomic_write`, maps `OSError` to `RunError` naming the user's output, never the temp file (§ 3.5). |
| (reused) `storage/files.os_reason(error: OSError) -> str` | The one translation of an `OSError` into lower-case words (`os.strerror(errno)`, first letter lowered through `domain/errors.lower_first`, the one implementation of that rule; `str(error)` when no errno). New, in `storage/files.py` because `storage/project_files` needs it too and storage may not import `cli`. |
| `_open_browser(output)` | `webbrowser.open`; a failure is a warning, exit 0 (§ 4). |
| `_summary(...) -> str` | The success summary (§ 7). |
| `run(options) -> None` | The flow of `docs/architecture.md` § Overview, unchanged in order. |
| `_say(stream, line)` | The one writer of our lines (progress, warnings, errors, summary); swallows `BrokenPipeError` on stderr. |
| `main(argv=None) -> int` | Parses with Typer, runs, maps every outcome to an exit code (§ 2). The only `try/except` that decides exit codes. |

M4.1 § 5 renames applied here: `nodes, relations = select(...)` → `tables, relations`; `dbt = read_manifest(...)` → `parsed`; `data = render_page(...)` → `page_bytes`; `note` → `layout_note`. `test_cli.OFFLINE` → `conftest.NO_PARSE_NO_OPEN`.

### 2. One error path (`main`)

```python
def main(argv: Sequence[str] | None = None) -> int:
    command = typer.main.get_command(app)
    try:
        parsed = command.main(
            args=list(sys.argv[1:] if argv is None else argv), prog_name=PROG, standalone_mode=False
        )
        if not isinstance(parsed, Options):  # --help / --version: click returned the exit code
            return int(parsed or 0)
        run(parsed)
    except click.UsageError as error:  # unknown option, bad choice, extra argument, empty value
        return _fail(_usage_message(error), 2)
    except (RunError, DomainError) as error:
        return _fail(str(error), 1)
    except (KeyboardInterrupt, click.Abort):
        return _fail("interrupted", 130)
    except BrokenPipeError:
        _silence_stdout()  # point fd 1 at os.devnull (Python docs recipe)
        return 1
    except Exception as error:  # a bug: still one line, never a traceback
        return _fail(
            f"internal error ({type(error).__name__}: {error}); please report it with the command you ran", 1
        )
    return 0
```

- `_fail(message, code)` writes `dbtscope: error: <message>` (whitespace collapsed to one line: the only place that collapses, storage and `_usage_message` leave it to `_fail`) on stderr through `_say` and returns `code`.
- `standalone_mode=False`: click does not print, does not call `sys.exit`, raises `UsageError` and returns the exit code of `--help` / `--version` (`click.exceptions.Exit`). Typer's own rich error panels and pretty tracebacks are therefore never used; `app` is also built with `pretty_exceptions_enable=False`. If the installed Typer does not return the callback's value with `standalone_mode=False`, the callback stores `Options` in a module-level holder reset by `main` (developer checks; the behaviour is the same).
- The script entry `dbtscope = "dbtscope.cli:main"` (unchanged) gets `sys.exit(main())`; `__main__.py` is unchanged (`raise SystemExit(main())`).
- **In-process change for tests:** `main(["--help"])`, `main(["--version"])` and usage errors now **return** 0 / 0 / 2 instead of raising `SystemExit`. The process exit codes are the same.
- Where errors are raised (D-028 "error classes"): `domain/` raises its `DomainError` subclasses; `storage/` raises those same classes for file content and read problems (it owns `_read_*`); `cli.py` raises `RunError` for what only the CLI can judge (paths given as options, dbt, the output, the browser, empty results) and converts every `OSError` it can meet at its own call sites (`subprocess.run`, `mkdir`, `atomic_write`) into `RunError` **at the call site**, because only there it knows which user path and which option to name. `main` is the only place that turns an exception into an exit code (responsibility map row "Map an error to a CLI exit code and message | `cli.main`", unchanged).

### 3. Paths: resolution, checks, messages

Rules (stated in `--help` and in every message):
- Every path printed is the **resolved absolute path** (`Path.resolve()`), in messages and in the summary (today `-o rel/map.html` and `--config` are printed as typed, #31, #46).
- `-o`, `--config`, `--manifest`, `--dbt` are relative to the **current folder**; `output:` and `layout_file:` of the config are relative to the **project folder** (unchanged behaviour, now said).
- An empty value of a path option (`""`) is a usage error, exit 2 (§ 8): the Typer callback of each path option raises `typer.BadParameter("must not be empty")`.
- `--dbt` given as a relative path is run as its absolute form: `subprocess.run(..., cwd=project)` would otherwise look it up relative to the project folder while `shutil.which` checked it relative to the current folder (found while designing, not in the sandbox).

**Unexpected `OSError`** (one the call sites above do not convert, e.g. an unreadable package file): `dbtscope: error: <reason> (<path>); check the installation`, exit 1: a problem of the environment, not a bug to report.

**Internal error**: any other exception: `dbtscope: error: internal error (<Type>: <message>); please report it with the command you ran`, exit 1. No environment switch to show the traceback (it would be new user-visible behaviour); developers reproduce through `main([...])` in a test.

### 5. Streams: what goes to stdout and stderr (decision D-029)

- **stdout: the result only**, i.e. the success summary (§ 7). Nothing else, ever.
- **stderr: everything about the run**: progress (`Running dbt parse in /abs/project...`, `Opening the page in the browser...`), **dbt's own output**, warnings and errors.
- dbt is run as `subprocess.run([dbt, "parse"], cwd=project, stdout=2, check=False)` (`2` = the process's standard error file descriptor, inherited by dbt; works on Windows too; `sys.stderr` is flushed first so our progress line comes before dbt's lines). dbt's stderr is already ours.
- When stderr is not a terminal and the user has not set `DBT_USE_COLORS`, dbt gets `DBT_USE_COLORS=false` in its environment (the command stays `dbt parse`): no `ESC[0m` in CI logs.

Why stderr for progress and dbt's output:
1. **An error sits next to its reason.** Today `dbtscope … > /dev/null` shows `dbt parse failed.` without dbt's message (#9–12), which is on stdout. With both on stderr, CI logs and terminals show the dbt error right above ours.
2. **stdout is a clean result channel.** The first stdout line is the absolute path of the page, so `page=$(dbtscope --no-open … | head -1)` or `2>/dev/null` gives exactly the result. Progress on stdout would pollute it.
3. **It is the Unix convention** (progress and diagnostics are not output: compilers, `curl`, `git clone`), and what dbtscope already does for its errors (D-004).
4. CI systems merge both streams, so the run reads in order there.

Rejected: everything on stdout (today: errors separated from their reasons, result polluted); everything on stderr (no result channel for scripts); a `--quiet` / `--verbose` option (a new option, outside the brief); capturing dbt's output and replaying it on failure only (loses live progress on large projects, and the user would not see dbt's warnings).

### 6. Typer interface

#### 6.1 App and options

```python
app = typer.Typer(
    add_completion=False,
    pretty_exceptions_enable=False,
    rich_markup_mode="rich",
    context_settings={"help_option_names": ["-h", "--help"]},
)
```

- `add_completion=False`: no `--install-completion` / `--show-completion` (new options are out of scope; no `shellingham` call at run time).
- `-h` kept: argparse provided it, scripts may use it.
- A single command: `dbtscope` with no arguments runs the map (`no_args_is_help=False`). No positional argument: `dbtscope myproject` is a usage error (§ 6.3).
- Flags declared with one name only (`typer.Option(False, "--no-parse")`), so Typer creates no `--parse` / `--no-offline` twins. The developer checks the rendered help lists exactly the 11 options plus `-h/--help`.
- Choices: `--preset` with `click_type=click.Choice(preset_names())` (the list read once from the package at import; no free text, so `""` and `../presets/x` are refused, #34, #35); `--view` with `click.Choice(get_args(View))` (`domain/config.View`, the one declaration of the values). `case_sensitive=True` (as today).
- Paths are plain `str` options checked by `_resolve` (§ 3), **not** `click.Path(exists=True)`: a missing file is an error (exit 1), not a usage error (exit 2), as today.

#### 6.2 Help

- Description (`HELP`): `Build the interactive map of a dbt project (universe of domains and ERD of tables) from its manifest, write it as one HTML page and open it.`
- Panels (`rich_help_panel`), in this order:
  - **Project**: `--project-dir` (`dbt project folder, holding dbt_project.yml [default: current folder]`), `--config` (`config file, relative to the current folder [default: <project-dir>/dbt-erd.yml if present]`), `--preset` (`built-in preset [choices]`).
  - **dbt**: `--no-parse` (`do not run dbt parse; read <project-dir>/target/manifest.json`), `--manifest` (`read this manifest.json instead of running dbt parse; dbt_project.yml is still needed for the config and the layout`), `--dbt` (`dbt executable, a name on PATH or a path [default: dbt]`).
  - **Output**: `-o/--output` (`HTML page to write, relative to the current folder [default: output: of the config, relative to the project, erd_output/erd.html]`), `--no-open` (`do not open the page in the browser`).
  - **Page**: `--view` (`tab shown when the page opens [default: view: of the config, universe]`), `--offline` (`embed the JavaScript libraries: the page works with no network (~2.5 MB more) [default: offline: of the config]`).
  - Default panel: `--version`, `-h/--help`.
- Epilog (`EPILOG`), each example on its own line (rich mode joins single newlines: use blank lines or `\b`-free markup, checked in the rendered help):
  ```
  dbtscope --preset data_vault                     in the project folder: parse, write, open
  dbtscope --no-open -o /tmp/map.html               batch / CI
  dbtscope --project-dir ../shop --no-parse         a project elsewhere, existing manifest
  dbtscope --manifest manifest.json --offline       a copied manifest, a page with no network
  Progress and dbt's output go to stderr, the summary to stdout. Exit codes: 0 success, 1 error, 2 usage, 130 interrupted.
  ```
- Help goes to stdout, exit 0. Rich honours `NO_COLOR` and the terminal width; tests set `COLUMNS=100` (and `TERMINAL_WIDTH`) for a stable rendering (M4.3 may check the README option table against it).
- `--version`: eager option, prints `dbtscope 0.2.0` on stdout, exit 0 (same text as today).

#### 6.3 Usage errors in the one-line format

Printed as `dbtscope: error: <that>` on stderr, **no usage block**, exit 2. Expected lines (click 8.1/8.2 wording; tests assert the prefix, the option name and the hint, not click's exact phrasing):

| Input | stderr |
|---|---|

## Rejected options

- **`click.Path(exists=True, dir_okay=…)` for path options**: turns a missing file into a usage error (exit 1 → 2 for every missing `--config` / `--manifest` / `--project-dir`) and prints click's message without our hints.
- **Typer in standalone mode with `rich` error panels**: multi-line boxed errors on stderr, breaks the one-line contract of D-004 and CI greppability.
- **`--preset` as free text validated in `run`** (exit 1, today): the brief asks for the presets as choices; a choice is a usage error by nature. Kept as exit 1 only for the file's `preset:` key.
- **A positional project argument or a `--project` alias**: forbidden by the user (brief, 2026-11-04).
- **A `--traceback` / `DBTSCOPE_DEBUG` switch for internal errors**: new user-visible behaviour, not in the brief.
- **Catching `OSError` once in `main`**: the message could not name the user's path or option (the temp file name would leak, #48) nor give the right hint.
- **Moving every path check into `storage/`**: storage does not know option names; the hints (`check --manifest`) belong to the CLI. Storage keeps what it reads (content, decoding, read errors).
- **Splitting `cli.py` into a package**: one outer module is enough (about 300 lines); a package would need a layering entry for no gain.
- **`typer-slim` without rich**: no `rich_help_panel` grouping, which the brief asks for.
- **Validating selectors eagerly in `Config`**: better locations (`select[0]: …`), but couples `config` to `selectors` and changes when an error is raised; the CLI prefix gives the file, which was the missing information.
- **A `Wrote <path>` first line**: reads better, but breaks `head -1` scripts and the entry-point test; the path alone is the result.

## UI design

The user-visible surface is the terminal: `--help`, progress lines, the success summary, warnings and errors. No page change (the reference pages stay byte-identical).

### Task and decision

| Who, when | Task | Decision | Information needed |
|---|---|---|---|
| Analyst or engineer, first run | Get the map of the project in front of them | Which option, if any, do I need? | One sentence of what the tool does, options grouped by what they act on, the default of each, four copyable examples |
| Engineer in CI | Script the page build | Where is the page, did it work? | Page path alone on stdout line 1, exit code, nothing else on stdout |
| Anyone, after a failure | Fix the run without reading code | What went wrong, on which file, what do I change? | One line: the file (absolute) or option, the reason, the next action; dbt's reason right above it |
| Anyone, after success | Check the page holds what they expect | Is it the right project, config, layout? | Counts per view, config and layout used, page size |

The frequent path is `dbtscope` with no option, from the project folder: the help says so in its first example.

### Help rendering: keep rich panels, markup mode `"rich"`, no `[` in our strings

- `rich_markup_mode=None` is **not** an option: Typer then falls back to click's plain formatter and drops the `rich_help_panel` groups the brief asks for (verified in `typer/core.py`, Typer 0.27.3). `"markdown"` would turn `_` and `*` in `dbt_project.yml`, `data_vault` into emphasis. Keep `"rich"`.
- Rule for the developer: no `[` in `HELP`, `EPILOG` or any option help (rich would read it as markup); a value that may hold one is passed through `rich.markup.escape`. Defaults are written in the help sentence (`Default: …`) with `show_default=False` on every option: Typer's own `[default: (x)]` adds parentheses around a custom text and cannot say "the view key of the config, else universe".
- Choices: `--preset` and `--view` get an explicit `metavar` (`NAME`, `VIEW`) and list the values in their help sentence, built from `preset_names()` and `get_args(View)` joined with `" or "`. Without the metavar, Typer 0.27.3 + click 8.5 prints `<function>` in the metavar column (verified); a `[a|b]` metavar widens the column and squeezes the help of the whole panel.
- Piped or `NO_COLOR`: rich drops colour and keeps the box-drawing characters (U+256D etc.); readable in any UTF-8 log and in a file. Rich falls back to ASCII boxes on a legacy Windows console. On a TTY, Typer's default help styling (bold option names) is kept: it is help, not an error or warning, and no new code is needed. Width: the terminal's, else `COLUMNS`, else 80. Rich pads each line with trailing spaces to the width: tests compare `rstrip()`ed lines.
- Typer version: Typer 0.12.5 with click 8.5 **crashes** on `--help` (`make_metavar() missing 1 required positional argument: 'ctx'`, verified). The developer sets the `typer` floor in `pyproject.toml` to a version verified with the locked click (0.27.3 is), not `>=0.12`, and checks that single `\n` in the epilog are kept (older Typer joined them).

Rules for warning and error text (D-029; the developer and the tests follow them; every message of § 3, § 4 and § 6.3 already does, except where corrected below):
1. Lower case after `error:` / `warning:`, except proper names and identifiers as written (`dbt_project.yml`, `PATH`, `Hub`, `UTF-8`, `JSON`, `YAML`). No final period, no `!`, no quotes around the whole message.
2. One line: whitespace of any inserted text (dbt, YAML, OS reasons) collapsed to single spaces.
3. **Paths**: always absolute and resolved, unquoted, preceded by their kind (`manifest`, `config`, `layout`, `output`, `project folder`) or by the option that gave them (`--project-dir`, `--config`, `--manifest`, `--dbt`, `--output`) when the message is about the option's value. A URI only where the user should paste it into a browser (`file://…`).
4. **Values that are not paths** (preset name, selector, field, the value of a choice) in single quotes: `unknown preset 'nope'`, `'bogus:x'`. Option names are never quoted in our hints (`check --config`); click's usage messages quote them (`'--view'`), kept as click writes them.
5. **Reasons from the OS** in lower case words after a colon: `cannot write <path>: permission denied`.
6. **Hint** after `; `, imperative, names the option or the action: `check --config`, `pass …`, `choose another --output`, `run dbt parse again`, `export it again from the page, or delete it`, `see dbtscope --help` (usage errors). Two exceptions with no hint, because the user did it on purpose: `interrupted`, and the silent broken pipe.
7. No colour, no symbols, no box: plain text whatever the terminal (user decision, § 6.4).

Messages of § 3–4 checked against these rules (all conform; the borderline ones):
- § 3 `--dbt name not found on PATH; check the name or pass its path`: keep (the value is an executable name, treated as a path: unquoted).
- § 4 browser warning: keep, it names a URI on purpose.
- § 4 `dbt parse failed with exit code 2 (see its messages above); …`: keep; "above" is true because dbt's output and our line share stderr (§ 5).

### Progress lines (stderr, exact)

Only where the user waits or where something visible happens; nothing for reading the manifest or rendering (sub-second to a few seconds, and the summary follows):

| When | Line |
|---|---|
| Before `dbt parse` (not with `--no-parse` / `--manifest`) | `Running dbt parse in <absolute project folder>...` |
| Before `webbrowser.open` (not with `--no-open`) | `Opening the page in the browser...` |

`sys.stderr` is flushed after each, so they come before dbt's lines and before the browser's own output.

### Success summary (stdout, exact)

```
/home/ana/shop/erd_output/erd.html
  universe: 1,482 tables in 14 domains, 2,310 relations, 4,077 lineage links
  detail:   38 tables (12 Hub, 9 Link, 17 Satellite), 41 relations
  page:     opens on universe, en, libraries from CDNs (1.4 MB)
  config:   /home/ana/shop/dbt-erd.yml, preset data_vault
  layout:   /home/ana/shop/dbt-erd-layout.json, saved 2026-11-01 10:00 UTC
```

- Numbers ≥ 1,000 written with a comma thousands separator (`f"{n:,}"`): the summary is read on large projects (~1,500 tables); English only (D-004), so the comma is right. Change from § 7, which wrote bare integers.
- Singular for 1: `1 table`, `1 domain`, `1 relation`, `1 lineage link` (today `1 tables`); kind labels stay as in the config (`1 Hub`).
- Empty detail: `  detail:   0 tables, 0 relations` (no parentheses) plus the § 4 warning on stderr. Empty universe: `  universe: 0 tables in 0 domains, 0 relations, 0 lineage links`.
- `page:` exactly `opens on <view>, <language>, libraries from CDNs (<size>)` or `opens on <view>, <language>, offline, libraries embedded (<size>)`; size `kB` below 1 MB (`{n/1000:.0f} kB`), else `{n/1e6:.1f} MB`.
- `config:` the file path, or `none (built-in defaults)`; then `, preset <name>` when `--preset` was given (`none (built-in defaults), preset star_schema`).
- `layout:` only when a layout is embedded; `, saved <YYYY-MM-DD HH:MM UTC>` when `savedAt` parses, the raw value when not, nothing when absent.
- Labels padded to 10 characters (`universe: ` is the longest), so values align.

### States, at a glance

| State | stdout | stderr | Exit |
|---|---|---|---|
| `--help` | help | — | 0 |
| `--version` | `dbtscope 0.2.0` | — | 0 |
| Running | — | progress lines, dbt's output | — |
| Success | summary | progress lines | 0 |
| Success with a problem | summary | progress + one `warning:` line per problem | 0 |
| Failure | — | progress, dbt's output if it ran, then exactly one `error:` line, last | 1 |
| Wrong option | — | one `error:` line ending `; see dbtscope --help` | 2 |
| Ctrl-C | — | `dbtscope: error: interrupted` | 130 |
| stdout closed | — | — | 1 |

### Accessibility of the terminal output

Plain text, one fact per line, no colour carrying meaning (the words `error` and `warning` do), no spinner or carriage-return redraw (screen readers and CI logs read every line once), paths in full so they can be copied. Help readable at 80 columns; at 60 columns the examples wrap but stay in order.
