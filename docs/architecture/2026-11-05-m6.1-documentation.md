## Chosen design

Two new documents and a slimmer README, under the rule of `docs/architecture.md` § Where facts live: each fact has one home; other files link to it.

| Document | Audience | Owns |
|---|---|---|
| `docs/user-guide.md` (new) | data engineers, analysts, business users preparing or attending the demo | install, upgrade, uninstall; usage modes; options; configuration and selectors; every page feature; troubleshooting; FAQ |
| `docs/how-it-works.md` (new) | curious users, reviewers, security and platform teams | the run from command to browser; what is read from the manifest; how a table is classified; what the page contains; how each view is laid out; the layout file's life; what never happens |
| `docs/architecture.md` (kept) | contributors | modules, layers and imports, responsibility map, glossary; links to `how-it-works.md` for concepts |
| `README.md` (slimmed) | everyone landing on GitHub | what it is, quick start, links |

Nothing is written twice: text moves out of the README (§ 4 lists every move). `how-it-works.md` explains in user terms and never names modules or functions; `architecture.md` keeps the module names and links to `how-it-works.md` for the concepts.

The developer writes only Markdown and tests. Nothing under `src/` changes, so the page and the M3 reference pages are untouched and the browser suite is not needed.

### 1. `docs/user-guide.md`

Headings below are exact; `##` headings are the anchors other files link to. Sentences are short; every command is in a fenced block with its language (`bash`, `powershell`, `yaml`, `text`) and copies as is; bash and PowerShell are both given wherever they differ. Concrete examples use `examples/acme_retail` (real names, real counts) or a generic `~/code/shop` project, as the README does today.

### 2. `docs/how-it-works.md`

For readers who want to understand, not to configure. No module or function names (those live in `architecture.md`); one link to `architecture.md` at the top and bottom. Mermaid diagrams follow the syntax rules of the M4.3 note § 3 (`flowchart TD|LR` or `sequenceDiagram`, quoted labels, no HTML, no `<br>`, no `<`, no `#`, no `;` in labels, no node id `end`).

```
# How dbtscope works
  who this is for; the code-level view is architecture.md

## The big picture                 diagram D1
## One run, step by step           diagram D2; the streams (result on stdout, the run on stderr), the atomic write
                                   ("the page is never left half-written"), exit codes: link user-guide.md#troubleshooting
## What is read from the manifest  diagram D3 and a table: manifest part -> what it becomes
                                   (models, seeds, snapshots, sources -> tables; columns with name, data_type, description;
                                   relationships and relationships_where tests -> relations; foreign_key constraints of
                                   contracts, column and model level -> relations; depends_on -> lineage; groups and owners;
                                   config meta.domain; tags, path, schema, database, package for selectors; packages only
                                   with include_packages). What is not read: SQL, run results, catalog.json, the warehouse.
                                   The developer checks every row against the manifest input models before writing.
## How a table is classified       diagram D4; home, for users, of the domain order (rule: D-015), of first-match-wins,
                                   of the default layers (first folder under models/, plus sources, seeds, snapshots,
                                   ordered by usual prefixes, said in words as the README does) and of the group (group_by)
## What the page contains          diagram D5: one HTML file = shell + styles + scripts + embedded JSON (both views'
                                   data and the layout file); libraries d3 and Viz.js from public CDNs, or embedded with
                                   --offline (versions and licences: link src/dbtscope/render/vendor/README.md);
                                   every < of the data escaped; the browser lays out and saves arrangements in localStorage
## How each view is laid out       universe: domains placed by a seeded force simulation, tables in layer bands inside the
                                   smallest circle, drawn on a canvas, same picture at every generation (D-040);
                                   detail: Graphviz, referenced tables left; flow: columns from lineage with layers as a
                                   floor, diagram D6 on a real acme_retail chain, cap 150 tables (D-036)
## The layout file's life          diagram D7
## What never happens              no warehouse connection, no credentials read by dbtscope, no rows or query results,
                                   no network while generating (libraries are vendored), no file written but the page
                                   (and dbt parse's own target/), no server; viewing a non-offline page loads two
                                   libraries from public CDNs
## Further reading                 architecture.md, decisions.md, ui-spec.md
```

### 6. Tests

Location: the option table test stays in `tests/unit/test_cli.py` (it belongs to the module that owns the options); the other checks go into a new `tests/unit/test_docs.py`. Path constants once, at the top of each file (`ROOT`, `USER_GUIDE = ROOT / "docs" / "user-guide.md"`, `HOW_IT_WORKS`).

6.1 `tests/unit/test_cli.py`, options table follows the guide:
- `readme_options()` becomes `guide_options()`: same parsing, reading `USER_GUIDE`, section `## Options` up to the next `## `; the failure message names `docs/user-guide.md`.
- `test_readme_options_match_the_command` becomes `test_guide_options_match_the_command`, same assertions; the exit-code sentence is asserted in `USER_GUIDE` (§ Troubleshooting moves there).
- `test_documented_commands_use_real_options` is parametrised over `README.md`, `CLAUDE.md`, `docs/user-guide.md`, `docs/how-it-works.md`, `examples/acme_retail/README.md`. Every option found must be a real option; the "at least one option" assertion stays for README, CLAUDE.md and the user guide only (`how-it-works.md` may hold no command). Write it as two parameters (`doc`, `has_commands`), not two tests.

6.2 `tests/unit/test_docs.py`, links and anchors (`README.md`, `CLAUDE.md`, `docs/user-guide.md`, `docs/how-it-works.md`, `docs/architecture.md`, `docs/ui-spec.md`, `examples/acme_retail/README.md`):
- every relative link `](path)` or `](path#anchor)` outside fenced blocks points to an existing file or folder;
- every anchor (in-file `](#x)` or into a `.md` file) matches a heading of the target, slugged as GitHub does: lower case, drop every character that is not a letter, digit, space, `-` or `_`, spaces to `-`, a repeated slug gets `-1`, `-2`. One helper `slug(heading)` and one `anchors(text)`; fenced blocks are skipped when reading headings.
- External `http(s)` links are not fetched (invariant 5).

6.3 Mermaid:
- `test_mermaid_blocks_follow_the_rules`: every ` ```mermaid ` block of the files of 6.2 starts with `flowchart TD`, `flowchart LR` or `sequenceDiagram`; no line holds `<`, `<br` or an odd number of `"`; in flowcharts no `;` and no `#` inside a label, no `end` as a node id (`-->\s*end\b`, `^\s*end\b` outside a sequence diagram's blocks).
- `test_mermaid_blocks_render` (opt-in, as `DBTSCOPE_DBT` for D-033): skipped unless `DBTSCOPE_MMDC` names a mermaid-cli executable; renders each block to SVG in `tmp_path` and expects exit code 0. Not marked `live`: it is local, but it needs Node and a Chromium, so it is opt-in. The developer runs it once if `mmdc` is available (`npx` is not used by the tooling); otherwise the reviewer checks the diagrams on GitHub after the push, and progress says so.

6.4 Config reference: the first ` ```yaml ` block of user guide § Configuration › Every key parses with PyYAML; its top-level keys equal `set(Config.model_fields) | {"preset"}`, the keys of its `universe` mapping equal `set(UniverseSettings.model_fields)`, and the mapping without `preset` validates with `domain/config.merge_config({}, mapping)` (`preset` is read by `storage/project_files.load_config`, not a `Config` field). A key added to `Config` and not documented fails here.

6.5 Example summary: the guide's ` ```text ` block under "Try it on the example project" shows the summary of acme_retail. The test builds the page with the `example_project` fixture (`--no-parse --no-open`, as the existing example tests) and asserts that the `universe:` and `detail:` lines of stdout appear verbatim in that block. The path and `page:` lines are not compared (they depend on the machine and on the page size).

6.6 Walkthrough excerpts: each ` ```yaml ` block directly preceded by the line `<!-- excerpt: examples/acme_retail/dbt-erd.yml -->` has every non-empty line present, in order, in that file. This is the only HTML comment form used in the guide.

6.7 Images (with § 7 only; written so that it passes with no image): every `![alt](…)` in the files of 6.2 has a non-empty alt and points to an existing file; every file in `docs/images/` except `README.md` is referenced; each PNG is at most 200 kB and the folder at most 1.2 MB.

## Rejected options

- **Keep everything in the README and add a table of contents**: about 600 lines today and more with uninstall, clone install, the walkthrough and the FAQ; a demo audience lands on a wall of text. The README stays the door, the guide the manual.
- **Several guide files (`docs/guide/install.md`, …)**: more links to keep alive and to test, and harder to search or print as one manual. One file with a table of contents is enough at this size; revisit above about 1,500 lines.
- **Merging "how it works" into `architecture.md`**: the audiences differ; module names and the responsibility map would bury the concepts, and concepts in user terms would bloat the contributor file.
- **Leaving the options table in the README**: the README would keep a reference section, against the landing-page goal; the test follows the table with a one-line path change.
- **Changing the CLI message "see the Configuration section of the README"** to point at the user guide: a code and message change, out of this documentation milestone; a two-sentence README § Configuration keeps it true. Listed in roadmap "Later".
- **Generating the options table or the config reference from code**: rejected in M4.3 (a tool and a step to forget); tests 6.1 and 6.4 find the same drift.
- **Rendering Mermaid in the default tests**: needs Node and a Chromium (D-019 spirit); static rules always, rendering opt-in.
- **A committed screenshot script** (`tools/doc_screenshots.py`, Playwright): code to maintain for seven images retaken a few times a year; the written recipe is enough. Revisit if images go stale often.
- **The page's own Export image for screenshots**: it omits the panels, bars and tabs that a guide must show.
- **A documentation site (MkDocs, GitHub Pages)**: new tooling and hosting for a private repository; GitHub renders Markdown and Mermaid already.
- **A French copy of the docs**: repository text is English (CLAUDE.md, Language convention); the page itself has French.
- **A new decision**: no system behaviour changes; "one place per fact" is already the rule (M4.3 note § 5). If the user approves § 7, the approval is recorded in this note and in progress, not as a decision.
