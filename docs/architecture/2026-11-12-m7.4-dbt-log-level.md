# M7.4 — dbt's warnings hidden by default, `--log-level` to show them (design note)

Status: APPROVED by the user (asked directly, 2026-11-12). Decision D-057.

## Context

**Request.** Run `dbt parse` so that only dbt's errors reach the terminal by default, and add `--log-level LEVEL` (dbt panel) to get dbt's more verbose output.

**Today.** `cli._dbt_parse` runs `[dbt, "parse"]` in the project, dbt's stdout on our stderr (D-029). On a real project dbt prints dozens of harmless `[WARNING]` lines (package macro YAML types, unused config paths) above dbtscope's summary. A failure is `ParseError("dbt parse failed (exit code N, see above)", …)`, mapped to the D-054 fallback or, with `--strict-parse`, to an error.

**dbt facts (dbt-core 1.5 to 1.12, click CLI).**
- `--log-level` is a global flag: choices `debug`, `info`, `warn`, `error`, `none` (env `DBT_LOG_LEVEL`). It sets the **console** level only; the file log has its own `--log-level-file` (default `debug`), so `logs/dbt.log` is unchanged. Left as is.
- Placement: before the subcommand (`dbt --log-level error parse`) is valid in every click-based version; after it (`dbt parse --log-level error`) depends on the version's per-subcommand global flags. **Chosen: before the subcommand.**
- At `error`, dbt still prints its failures: `Encountered an error: …`, profile, project, package and compilation errors are fired at error level. `[WARNING]`, `Running with dbt=…` and the parse timing lines are hidden. So "see above" stays true.
- At `none`, dbt prints nothing, errors included.
- dbt Fusion: clap CLI with a global `--log-level`; not verified here. If a dbt rejects the flag, it exits non-zero with its usage error (printed whatever the level) and the D-054 fallback or `--strict-parse` applies as for any failure. The developer checks `dbt --help` of a Fusion build when one is at hand and records the result in `docs/progress.md`.

## Chosen design

Only `src/dbtscope/cli.py` changes.

- **Type.** `LogLevel = Literal["debug", "info", "warn", "error", "none"]` in `cli.py` (a CLI concern, not a config key; the domain is not touched). `DEFAULT_LOG_LEVEL = "error"`.
- **Option.** `--log-level LEVEL`, panel `dbt`, typed `LogLevel | None`, default `None` (so that "given" is known), help: `dbt's console log level: debug, info, warn, error, none (passed to dbt parse). Default: error, dbt's errors only.` `Options.log_level: LogLevel | None = None`.
- **Conflicts.** `--log-level` with `--no-parse` or `--manifest` is a usage error (exit 2): `'--log-level': cannot be used together with --no-parse` (or `--manifest`). One implementation for both flags: the existing `--strict-parse` check becomes a loop over the dbt-run-only options given (`--strict-parse`, `--log-level`), same message form (invariant 2).
- **Run.** `_parse(inputs, strict, log_level, now)` passes the effective level (`options.log_level or DEFAULT_LOG_LEVEL`) to `_dbt_parse(dbt, project, log_level)`, which runs `[dbt, "--log-level", log_level, "parse"]`. The flag is always passed, even at the default: dbtscope's level wins over a `DBT_LOG_LEVEL` in the environment (the CLI flag outranks the env var in dbt); users choose with `--log-level`.
- **Messages.**
  - `Running dbt parse in <project>...` stays at every level (dbtscope's line, not dbt's).
  - Failure reason at every level but `none`: unchanged, `dbt parse failed (exit code N, see above)`.
  - At `none`: `dbt parse failed (exit code N; --log-level none hid dbt's messages)`. The hints, the fallback warning (D-054) and the strict error are otherwise unchanged; the reason feeds them as today.
  - `cannot run <dbt>: …` and `dbt not found on PATH` are unchanged (dbt never ran).
- **Responsibility map.** Row "Run dbt parse, or fall back …" (`cli._parse`) is unchanged in owner; its text gains "at the console log level of `--log-level` (D-057)". No new module, no data format change, no migration, nothing new on disk.

## Rejected options

- **`dbt parse --log-level error`** (after the subcommand): not accepted by every supported version.
- **`DBT_LOG_LEVEL=error` in dbt's environment** instead of the flag: equivalent in dbt-core, but an unsupported dbt would ignore it silently, and the argv would not show what dbtscope asks.
- **`--quiet` / `-q`**: hides non-error output, but gives no way to more verbose output; one option covers both.
- **Filtering dbt's output in Python**: dbt's output is streamed, not parsed (D-029, D-054).
- **Honouring `DBT_LOG_LEVEL` when set** (pass no flag): a second way to set the same thing, and the default would then depend on the environment.
- **Making `none` refused**, or keeping "see above" at `none`: the first removes a dbt value the user asked to mirror, the second points at nothing.
- **Changing `--log-level-file` or `--log-path`**: `logs/` is dbt's own business, written as before (how-it-works § What never happens).

## Impacts

- **Proposed decision** (append to `docs/decisions.md` with the code):

  > **D-057 — dbt parse runs with `--log-level error` by default; `--log-level` changes it.**
  > Asked by the user on 2026-11-12 (M7.4, design note `docs/architecture/2026-11-12-m7.4-dbt-log-level.md`), after dozens of harmless dbt warnings buried the summary on a real project. dbtscope runs `dbt --log-level <level> parse` (global flag before the subcommand, valid from dbt-core 1.5), `<level>` from the new dbt-panel option `--log-level` (`debug`, `info`, `warn`, `error`, `none`, dbt's values), default `error`: dbt's errors are still shown, its warnings and info lines are not. The flag is always passed, so it overrides `DBT_LOG_LEVEL`. It sets the console only: dbt's `logs/dbt.log` is unchanged. `--log-level` with `--no-parse` or `--manifest` is a usage error (exit 2), like `--strict-parse`. At `none` the failure reason says `--log-level none hid dbt's messages` instead of `see above`. Refines D-029 (dbt's output on stderr, now filtered by dbt itself), D-026 (one more dbt-panel option) and D-054 (unchanged fallback, reason wording at `none`). D-012 holds: `dbt parse` is still the only dbt command. Rejected: the flag after the subcommand, the `DBT_LOG_LEVEL` env var, `--quiet`, filtering dbt's output, honouring `DBT_LOG_LEVEL`.

- **Docs:** `docs/user-guide.md` (options table, dbt panel; § what is printed; troubleshooting row "dbt parse failed" mentions `--log-level info` to see dbt's warnings, plus the `none` wording; CI recipe unchanged), `docs/how-it-works.md` (run diagram: `dbt --log-level error parse`), `docs/architecture.md` (responsibility map row text), `--help` epilog if it lists dbt's command, roadmap M7.4, progress, CHANGELOG.
- **Compatibility:** same page, payloads and files (D-013 untouched); fewer stderr lines by default; exit codes unchanged. `tools/example_manifest.py` (calls `cli.main`) gets the default; the committed manifest is unaffected.

- Default run: `command == [found_dbt(), "--log-level", "error", "parse"]`; update `test_dbt_runs_in_the_project_with_its_output_on_stderr` and any other test asserting `[found_dbt(), "parse"]`.
- Parametrised over `debug`, `info`, `warn`, `error`, `none`: `--log-level X` gives `[…, "--log-level", X, "parse"]`; stderr still starts with `Running dbt parse in …`.
- A bad value (`--log-level verbose`, `--log-level ERROR` if Typer is case-sensitive: decide by Typer's behaviour and assert it) is a usage error, exit 2, naming the choices.
- `--log-level info --no-parse` and `--log-level info --manifest <file>`: exit 2, one line `'--log-level': cannot be used together with --no-parse` / `--manifest`; the `--strict-parse` conflict tests stay green unchanged.
- Failure, code 2, default level: reason `dbt parse failed (exit code 2, see above)` in the fallback warning and with `--strict-parse` (existing tests unchanged).
- Failure at `--log-level none`: reason `dbt parse failed (exit code 2; --log-level none hid dbt's messages)`, in the fallback warning and in the strict error.
- `DBT_LOG_LEVEL=info` in the environment: the argv still carries `--log-level error`.
- `fake_dbt_executable` (real process, `tests/integration/test_entry_points.py` style): the script writes its argv to a file; assert `--log-level error` comes before `parse`.
- Docs: the options-table test in `tests/unit/test_docs.py` sees `--log-level` in the user guide; `tools/doc_consistency.py` passes.
- Manual (developer, recorded in `docs/progress.md`): `examples/acme_retail` with dbt-duckdb at `error` (no `[WARNING]` lines) and `info` (as before); a broken model at `error` still shows dbt's error.
