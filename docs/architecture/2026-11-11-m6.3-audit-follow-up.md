## Chosen design

### 1. One display-name rule (audit option b), D-054

**The rule:** the display name of a domain, layer or kind is its `label` when that is a non-empty string, else its `key`. `||`, not `??`: `label: ""` shows the key, as domains already do, and as the audit's "`label or key`" for the summary does. A whitespace-only label is shown as written (the user wrote it; the same in both runtimes: `" " || key` and `" " or key` both keep it). The rule exists once per runtime, each named in the responsibility map:

- **Page:** `common.js labelOf = item => item.label || item.key` (comment updated: "its label, or its key when the config set `label: null` or an empty label (D-054)").
- **Python:** new `domain/classify.display_name(key: str, label: str | None) -> str` returning `label or key`. `classify` is the module of rules shared by both views and already holds `OTHER`; it imports nothing new. Used by `cli._summary` (`{display_name(k.key, k.label)}`), the only Python place that shows a label to a person. Not used by `_domains` (see below).

**`domain/` passes the label through for every rule.** `_domains` becomes `label = rule.label if rule else key` (no rule: the key, unchanged; the no-domain entry keeps `NO_DOMAIN[lang]` and `NO_DOMAIN_COLOR`; colour logic unchanged). `_layers`, `_kinds`, `detail_data` are unchanged. Payload types stay `str | None` (no model change; `UniverseDomain.label` is already `str | None`).

**Payload change, exactly:** only the universe payload of a config with a `domains` rule whose `label` is `null` or `""` changes, that domain's `"label"` becoming `null` / `""` instead of its key. Among the reference pages: `layers_domains` only, one field (`"key":"raw","label":"raw"` → `"label":null`). The example project and the `shop` defaults have none.

**What a viewer sees:** for domains, nothing changes in any config (the page now applies to `null` / `""` the same fallback Python applied). Visible fixes: a layer or kind with `label: ""` shows its key (was blank) everywhere; a detail kind with `label: null` or `""` shows its key in the Types filter (was blank); the CLI summary prints the key (`1 stage`, was `1 None` / `1 `).

**Page sites** (each through `labelOf`): `flow.js domainLabel` (`labelOf(DOM[N[i].domain])`), `domainList` (sort, summary title, rows: compute `name = labelOf(DOM[k])` once per row), `universe.js renderBar` (`labelOf(DOM[k])`), `detail.js refreshControls` (`label: labelOf(k)`, possible once the local function is renamed, § 3). After the change, `\.label\b` appears in the assets only inside `labelOf` (a unit test keeps it so).

### 2. The page's layout import applies `check_layout`'s checks

In `boot.js`, next to `LAYOUT_FORMAT`:

```js
const LAYOUT_VERSION = 1;   // domain/layout.LAYOUT_VERSION; a file without `version` is accepted
const LAYOUT_SECTIONS = ['universe', 'detail'];   // domain/layout.LAYOUT_SECTIONS: mappings when present
```

and one predicate, `readableLayout(d)` (the page's counterpart of `domain/layout._problem`): `d` is a plain object (not `null`, not an array), `d.format === LAYOUT_FORMAT`, `!('version' in d) || d.version === LAYOUT_VERSION`, and every section of `LAYOUT_SECTIONS` present in `d` is a plain object. The import handler replaces `if (d.format !== LAYOUT_FORMAT) throw …` with `if (!readableLayout(d)) throw …`; a refused file shows the existing `L.bad` alert ("Not a dbt-erd layout file." / its French) and changes nothing (no `LAYOUT.load`, no relayout, localStorage untouched). `dump` writes `version: LAYOUT_VERSION`. Invariant 9 / D-013 untouched: same format, version, file name and storage key; only what the page accepts narrows to what the CLI accepts.

Accepted difference: JSON `1.0` is the float `1.0` for Python (refused, `type(version) is not int`) and the number `1` for JavaScript (accepted). The page never writes `1.0`; a hand-edited `1.0` loads in the page and is refused by the next run with D-029's one-line message. Not worth a raw-text check.

The embedded layout is already checked by the CLI; the browser's own localStorage copy is written by the page and is not re-checked (out of scope).

### 3. Shared page helpers (audit § 2 suggestions)

- **`common.js placeTip(tip, box, x, y)`**: shows the already-filled `tip` near the client point `(x, y)` inside `box` (the tip's positioned container): 14 px right of and below the point; flipped to the left when it would cross the box's right edge less 8 px, then above when it would cross its bottom edge less 8 px; never closer than 8 px to the left or top edge. Exactly `flow.js showTip`'s current placement, moved. `flow.js showTip` keeps its touch check and content and calls `placeTip(tip, box, x, y)`; `universe.js` calls `placeTip(tip, stage, ev.clientX, ev.clientY)` instead of its clamp. The `#f-tip` max-width rule moves to `.tip` (`max-width:min(360px, calc(100% - 16px)); box-sizing:border-box`), so both tooltips fit a 360 px stage. Visible change, universe only: near the right edge the tooltip goes to the left of the pointer instead of sliding under it, and near the bottom it goes above it (the M5.3 note already described `#u-tip` as "flips left/up near the edges").
- **`common.js colorDot(color)`**: a new `<i>` painted by `paintDot` (the one dot element of lists and filter rows). Used by `filterRow`, `flow.js` (the summary dots and domain rows) and `universe.js renderBar`. `paintDot` stays the one painter (also used on existing elements: `#u-tj-dot`, `#f-dot`).
- **`common.js listRow(mark, text, count)`**: an `<li>` holding `mark` (an element), the text in a `<span>` (`textContent`) and, when `count` is given, a `<small>` with it. Replaces `flow.js row` (also used there with the legend marks `legendMark('start' | 'up' | 'down')`, which is why the helper takes a mark, not a colour) and the `<li>` of `renderBar` (`listRow(colorDot(DOM[r.k].color), r.text)`). The universe bar row gains a `<span>` around its text: same text content, same look (`.tj-pop li` is a flex row; a text node and a span are both flex items).
- **`detail.js`**: the local `labelOf` (an entity's name, prefixed with its group when foreign) becomes `entityName`: its declaration (line 42) and its six uses (lines 77, 106, 107, 112, 148, 224). The shadowing note leaves `render/CLAUDE.md`.

No new strings, no new colours, no payload change from this section.

### 4. Kind fallback: kept, documented

The detail view keeps `OTHER` for every table no `kinds` rule matches; the universe keeps `TYPE_KINDS` first. Reasons: the detail is the ERD of the configured classification (its kinds carry the body tint `bg`, and its default scope is `type:model`, where `TYPE_KINDS` never applies); the difference is already documented for users (`how-it-works.md` § How a table is classified); unifying would change the detail payload of every config that selects sources, seeds or snapshots into the detail, for no reported need. Add to `domain/CLAUDE.md` (rules list): "A table no `kinds` rule matches is `OTHER` in the detail (configured kinds only, the ERD's classes) and `TYPE_KINDS[resource_type]`, else `OTHER`, in the universe (where sources, seeds and snapshots are a third of the map): intended, documented in `how-it-works.md`; not one `kind_of`."

## Rejected options

- **Option (a), Python resolves every label** (`_layers`, `_kinds`, `detail_data` through `display_name`): changes the payload of every config with `label: null` on a layer or kind (three reference payloads, `layers_domains` and `kinds`) and keeps `labelOf` in the page anyway for older payloads; the rule would still exist twice. The user chose (b).
- **`??` (null only) as the rule:** `label: ""` would become a blank domain name in the page, a regression from today's Python fallback, and the CLI's `label or key` would differ from the page.
- **Keeping `_domains`' fallback and only fixing the page sites:** the rule would stay in three places (audit § 2).
- **`display_name` in `domain/payload` or on the payload models:** `payload.py` holds no logic (`domain/CLAUDE.md`).
- **`display_name` in `cli.py`:** a display rule is domain logic, and `domain/` is where its Python home is testable without the CLI.
- **Sharing the layout check by embedding a JSON schema or the checks' result in the payload:** a second format to keep; the predicate is five conditions mirrored with their source named, and the same cases drive the Python and browser tests (Test plan).
- **`dotRow(color, text, count)` as the audit sketched:** the flow list mixes colour dots and legend marks in the same rows; `listRow(mark, …)` + `colorDot` covers both with no special case.
- **Unifying the kind fallback (`kind_of` in `classify`):** see § 4.
