# M4.2b — Preset files and strict preset validation (design note)

Status: DONE (built, tested and reviewed on 2026-11-04). The request and its four decisions come from the user (2026-11-04). The choices made here stay inside them: which keys a preset may hold, the name-or-path rule, the error wording, and naming the applied preset in the summary. D-030 refines D-015 and D-028 and does not reverse them. D-013 is not superseded (§ 6).

## Context

Request: let a run start from a preset kept in a YAML file. The file is given by a new option `--preset-file <path>` or by a path in the `preset:` key of `dbt-erd.yml`. Every preset, external or built-in, is validated strictly on its own before the merge, while `dbt-erd.yml` stays lenient. Roadmap: M4.2b (new, under M4).

Current code:
- `storage/project_files.read_preset(name)` reads `presets/<name>.yml` by name only and returns the raw dict without validating it. A bad key in a preset is ignored silently, because `Config` uses `extra="ignore"`.
- `load_config(project_dir, config_path, preset)` merges defaults < preset < file through `domain/config.merge_config(preset_dict, file_dict)`, which validates once. An unknown name in the file's `preset:` key gives `config <path>: unknown preset 'x'; choose …` with exit 1.
- `cli.py`: `--preset` is a `Literal` of `preset_names()`, so an unknown name, `""` or a path gives exit 2 (D-029). `Report.preset` is the `--preset` value only. `_config_label` falls back to `preset <name>`.
- Built-in presets `data_vault.yml` and `star_schema.yml` use only `title`, `group_by`, `key_columns`, `select`, `exclude` and `kinds`.

Hard constraints:
- No option is renamed, only added. `--project-dir` stays the only project option.
- Exit codes 0 / 1 / 2 / 130 (D-029).
- The page stays byte-identical (`tests/fixtures/m3-reference-pages/` is never regenerated).
- `domain/` stays pure.
- The `dbt-erd.yml` format may only be extended (invariant 9, D-013).

## Chosen design

### 1. What a preset may contain

A preset describes conventions: naming, kinds, domains, layers, scope, opening state. It is meant to be shared between projects. It may hold every `Config` key **except**:

| Key | Why it is refused in a preset | Problem text |
|---|---|---|
| `preset` | A preset must not chain to another preset. One level keeps the precedence readable and rules out cycles. | `a preset cannot load another preset` |
| `output` | A path relative to each project's folder. In a shared preset, every project using it would write to the same relative place without saying so in its own config. The page path is a project decision. | `belongs to dbt-erd.yml, not to a preset` |
| `layout_file` | The layout is the per-project shared arrangement (D-013). Pointing many projects at one layout name from a preset is a trap. | `belongs to dbt-erd.yml, not to a preset` |

Allowed keys: `title`, `language`, `view`, `offline`, `select`, `exclude`, `group_by`, `key_columns`, `include_packages`, `kinds`, `domains`, `layers` and `universe` (`select`, `exclude`, `links`, `detail`, `hidden_kinds`). In rules (`kinds`, `domains`, `layers`) the allowed keys are `key`, `label`, `color` and `match`. `title`, `language`, `view` and `offline` stay allowed: a team preset may set its language or its offline default, and the built-in presets already set `title`. The built-in presets hold no refused key, so they are valid unchanged.

### 2. Strict validation, reusing the config models (domain)

In `domain/config.py`, the new classes are subclasses of the existing models, not a parallel schema. The fields, the types and the validators (`_group_by`, `_key_columns`, `_label_defaults_to_key`) are inherited. Only the extra policy changes, plus the nested types that must carry it:

```python
PRESET_SETTINGS = ConfigDict(extra="forbid", frozen=True)  # a preset is closed: a misspelt key is an error (D-030)
NOT_IN_PRESET = {
    "preset": "a preset cannot load another preset",
    "output": "belongs to dbt-erd.yml, not to a preset",
    "layout_file": "belongs to dbt-erd.yml, not to a preset",
}

class PresetRule(Rule):                 model_config = PRESET_SETTINGS
class PresetUniverse(UniverseSettings): model_config = PRESET_SETTINGS
class Preset(Config):
    model_config = PRESET_SETTINGS
    kinds / domains / layers: Annotated[tuple[PresetRule, ...], BeforeValidator(_as_list)] = ()
    universe: PresetUniverse = PresetUniverse()
    @model_validator(mode="before")  # refuse NOT_IN_PRESET keys, in that order: ValueError(f"{key}: {problem}")

def check_preset(data: dict[str, Any]) -> dict[str, Any]:
    """`data` unchanged if it is a valid preset; else ConfigError(validation_message(...))."""

def is_preset_path(value: str) -> bool:
    """A `preset:` value names a file when it holds `/` or `\\` or ends with .yml / .yaml (any case)."""
```

- `check_preset` returns its input **unchanged**. `storage/` passes that same raw dict to `merge_config`, exactly as today. The validation therefore cannot change what is merged: the built-in presets give the same `Config` and the same page bytes. `Preset` is only a validator and is never used as the run's config. Rejected: passing `Preset(...).model_dump(exclude_unset=True)` on to the merge. It would turn lists into tuples, fill rule labels and kind colours, and add a risk to byte identity for no gain.
- **Strict types.** A preset uses the same field types as `Config`. Those types are already strict where it matters: `StrictBool` (`offline: "yes"` and `include_packages: 1` are refused), `Literal` choices (`language: EN` is refused), and `str` without number coercion (`key_columns: 5` and `match: [1]` are refused). The only conversions kept are the two shorthands of the config syntax: a single string is a one-item list, and a YAML number in `title` or rule `label` is its text. A preset's content is then valid in `dbt-erd.yml` and the reverse holds too, apart from the refused keys. Rejected: pydantic `strict=True`. In Python mode it accepts only `tuple` instances for tuple fields (YAML gives lists) and only model instances for nested models, so it would refuse every built-in preset. Working around that would need a second, parallel schema.
- `domain/errors.PROBLEMS` gains `"extra_forbidden": "unknown key"`. Today only `model.DOMAIN` models forbid extras, and those are built by dbtscope, so no existing user-facing message changes.
- **Name or path** (`is_preset_path`): the value is a path when it contains `/` or `\`, or ends with `.yml` / `.yaml` (case-insensitive); otherwise it is a built-in name. Built-in names are identifiers (`data_vault`), so they can never look like paths. `preset: team.yml` is a file next to the config, and `preset: ./team` is a file named `team`. No `~` or variable expansion, as for `output` and `layout_file`. This rule lives in `domain/` because it is a pure string rule. `storage/` applies it.

### 3. Reading presets (storage)

`storage/project_files.py`:
- `read_preset(name)`: unchanged contract (built-in by name only, returns a dict). It now validates through `check_preset`. A failure is `preset <name>: <key>: <problem>; check the installation`. That can only be a packaging bug, and the test of § Test plan rules it out.
- New `read_preset_file(path: Path, setting: str) -> dict[str, Any]`. `path` is absolute. `setting` names where the path came from, for hints: `--preset-file` or `preset in config <abs path>`. One `path_kind` call (the one check of a user-given path), then `_read_yaml(path, f"preset {path}")` (reused: UTF-8, YAML, mapping), then `check_preset`. Errors are prefixed `preset <path>: ` and followed by `; fix the file` (`CONFIG_HINT`).
- `load_config(project_dir, config_path=None, preset: str | Path | None = None)`. A `str` is a built-in name (from `--preset`) and a `Path` is a file (from `--preset-file`, already absolute). The command line overrides the file's `preset:` key. When the CLI gives a preset, the key's file is not read, even if it is missing. When the key is used:
  - Any false value (`None`, `""`, `false`, `0`, `[]`, `{}`): no preset (unchanged, invariant 9; review loop 1).
  - A true value that is not a string: `config <cfg>: preset: must be a string; fix the file`.
  - `is_preset_path(value)`: `read_preset_file((cfg.parent / value.replace("\\", "/")).resolve(), f"preset in {config_source(cfg)}")`. A relative path is read from the **config file's folder**, so `--config other/x.yml` reads `other/<value>`. Every `\` is a folder separator, so a `dbt-erd.yml` written on Windows (`conf\team.yml`) works on Linux and macOS (review loop 1).
  - Otherwise: `read_preset(value)`, with the existing `config <cfg>: ` prefix on an unknown name.
- `LoadedConfig` gains a third field, `preset: str | Path | None`: the preset actually applied (a built-in name, or the absolute path of a file), whatever its origin. The CLI uses it for the summary and for `_config_label`.
- One dispatch helper, `_load_preset(reference: str | Path, setting: str) -> dict[str, Any]`, is used by both branches of `load_config` (with and without a config file). It does not duplicate the no-file branch.

### 4. Command line (cli.py)

- New option `--preset-file`, declared with `_path_option("--preset-file", metavar="FILE", panel="Project", help=…)`, placed right after `--preset`. An empty value is a usage error with exit 2 (the existing `_not_empty` callback). Help: `Conventions from a YAML file instead of a built-in --preset: the keys of dbt-erd.yml except output, layout_file and preset.` (no `[`). `--preset-file` has the same length as `--project-dir`, so the option column and the 80-column help keep their widths. Epilog unchanged: the existing examples cover the common runs, and a fifth example adds little.
- `--preset` and `--preset-file` together: `command` raises `typer.BadParameter("cannot be used together with --preset", param_hint="'--preset-file'")`. `BadParameter` is the only usage exception Typer exports publicly, and `main` already catches it as `typer.TyperException` with exit 2. The resulting line is `dbtscope: error: invalid value for '--preset-file': cannot be used together with --preset; see dbtscope --help`. Click's wording may vary, so tests assert the exit code, both option names and the hint.
- `Options` gains `preset_file: str | None`. `_resolve` resolves it to an absolute `Path` (`Inputs.preset_file`). The checks (missing, folder, refused, content) are done once, by `storage/project_files.read_preset_file`, because the `preset:` key needs exactly the same checks and only storage sees it. The responsibility map row "Resolve and check the paths given on the command line" says so. `--config` keeps its double check (M4.2 § 3).
- `run` passes `inputs.preset_file or options.preset` to `load_config`.
- Summary (`_summary`): `Report.preset` takes `LoadedConfig.preset`. The `config:` line ends with `, preset <name or absolute path>` **whenever a preset was applied**:
  - `config:   /home/ana/shop/dbt-erd.yml, preset /home/ana/conventions/team.yml`
  - `config:   none (built-in defaults), preset /home/ana/conventions/team.yml`

  This is a small change: a built-in preset set by the file's key (`preset: data_vault`) is now named too. Before, only `--preset` was named. It is the same rule for every origin, and it is what the user asked for files.
- `_config_label` falls back to `preset <name or absolute path>` from the same value.

### 5. Errors (one line, D-029 form; exit 1 unless stated)

Here `<p>` is the absolute preset path and `<cfg>` the absolute config path. The hint `<origin>` is `--preset-file` or `preset in config <cfg>`.

| Case | Message after `dbtscope: error: ` |
|---|---|
| `--preset-file ""` | `invalid value for '--preset-file': must not be empty; see dbtscope --help` (exit 2) |
| `--preset` + `--preset-file` | `invalid value for '--preset-file': cannot be used together with --preset; see dbtscope --help` (exit 2) |
| missing | `preset <p> not found; check <origin>` |
| a folder | `preset <p> is a folder; check <origin>` |
| not a regular file (FIFO, device) | `preset <p> is not a regular file; check <origin>` |
| refused path (name too long, EACCES on a parent) | `cannot use preset <p>: file name too long; choose a shorter <origin>`. Built by `refused_hint(error, origin)`, which gives `check <origin>` for other errnos. |
| unreadable | `cannot read preset <p>: permission denied; check the file` (`_read_text`) |
| not UTF-8 | `preset <p> is not UTF-8 (invalid byte at offset N); save it as UTF-8` |
| bad YAML | `preset <p> is not valid YAML (line 2, column 1: …); fix the file` |
| not a mapping | `preset <p> must be a mapping of settings; see the Configuration section of the README` |
| unknown or misspelt key | `preset <p>: kinds[0].colour: unknown key; fix the file`, or `preset <p>: tittle: unknown key; fix the file`; shown before any other problem of the preset (`validation_message(..., first="extra_forbidden")`, review loop 1) |
| refused key | `preset <p>: output: belongs to dbt-erd.yml, not to a preset; fix the file`, or `preset <p>: preset: a preset cannot load another preset; fix the file` |
| wrong type | `preset <p>: offline: must be true or false; fix the file`, or `preset <p>: language: must be 'en' or 'fr' (and 1 more problem); fix the file` |
| `preset:` key not a string | `config <cfg>: preset: must be a string; fix the file` |
| `preset:` key, unknown name | `config <cfg>: unknown preset 'nope'; choose data_vault or star_schema, or give the path of a preset file`. The hint is extended; the rest is unchanged. |
| `--preset ../x.yml` | exit 2, `invalid value for '--preset': … (or use --preset-file for a preset file); see dbtscope --help` (D-029; hint added in review loop 1) |

An empty preset file (empty YAML) is a valid empty preset, as an empty `dbt-erd.yml` is valid today. Nothing is written on any failure: the config is loaded before dbt runs and before the page is written.

### 6. Data format and decisions

- **`dbt-erd.yml` (invariant 9, D-013).** This is an extension and needs no superseding decision or migration. A `preset:` value that `is_preset_path` treats as a path (one holding `/` or `\`, or ending with `.yml` / `.yaml`) can never be a built-in name, so before M4.2b it always failed with `unknown preset` (exit 1). Every file that worked before keeps working with the same meaning. Unknown keys in `dbt-erd.yml` stay ignored (`SETTINGS` is unchanged).
- **Built-in presets:** files unchanged. Validation returns the same dict, so the pages are identical.
- **Decisions:** D-030 (below, appended to `docs/decisions.md`) refines:
  - D-015 ("presets are plain config files": they are now a closed subset of the config keys, and can be files);
  - D-028 (a third pydantic policy, `config.PRESET_SETTINGS`, for presets only);
  - D-029 (summary names the applied preset; new usage error).

  D-004, D-013, D-026 and D-029's exit codes hold.

**D-030 text:**

> **D-030 — A preset can be a YAML file; every preset is validated strictly on its own.**
> Settled with the user on 2026-11-04 (M4.2b, design note `docs/architecture/2026-11-04-m4.2b-preset-file.md`).
> - **Loading.** A preset is a built-in name (`--preset`, choices unchanged, D-026/D-029) or a YAML file. The file is given by the new option `--preset-file <path>` (relative to the current folder) or by the `preset:` key of `dbt-erd.yml`. In that key, a value holding `/` or `\` or ending with `.yml` / `.yaml` is a path, read from the config file's folder; any other value is a built-in name. `--preset` together with `--preset-file`, or an empty `--preset-file`, is a usage error (exit 2). Precedence holds: defaults < preset < config file < command line, and a command-line preset replaces the key.
> - **Validation.** Before the merge, a preset (built-in or file) is validated on its own by `domain/config.Preset`, a subclass of `Config` (rules `PresetRule`, universe `PresetUniverse`) with `PRESET_SETTINGS = ConfigDict(extra="forbid", frozen=True)`. An unknown key, a key of the refused list (`preset`: no chaining; `output` and `layout_file`: project paths) and a wrong type are each one line, `preset <abs path or name>: <key>: <problem>; fix the file`, exit 1. Types are those of `Config`. The only conversions accepted are the config's two shorthands (one string for a list, a number for `title` / `label`). The validated dict is merged unchanged, so built-in presets give the same pages.
> - **Summary.** It names the applied preset, built-in or file, as `, preset <name or abs path>`.
> - **Relation to earlier decisions.** `dbt-erd.yml` stays lenient (unknown keys ignored, invariant 9), and its format is only extended: every value now read as a path was an `unknown preset` error before, so no decision supersedes D-013. This refines D-015 (presets are plain config files: now a closed subset of the config keys, built in or external) and D-028 (a third model policy, `PRESET_SETTINGS`, for presets only; `DOMAIN` and `SETTINGS` unchanged).
> - **Why.** Teams share their own conventions without forking the package, and a misspelt key in a preset fails loudly instead of being ignored.
> - **Rejected.**
>   - pydantic `strict=True` (refuses YAML lists and nested mappings, so it would need a parallel schema).
>   - Making `dbt-erd.yml` strict too (breaks existing files, invariant 9).
>   - Accepting a path in `--preset` (changes an option's meaning and D-029's exit code).
>   - Chained presets.
>   - Preset paths relative to the project folder (the preset sits next to the config that names it).

## Rejected options

- **A separate `PresetSettings` schema** listing the allowed keys again: two schemas to keep in sync (D-006). Subclasses inherit fields, types and validators.
- **A shared base class `Conventions`, with `Config` adding `output` / `layout_file`:** removes the before-validator, but reorders `Config`'s fields and touches the model every run uses, for a clearer message we get anyway from `NOT_IN_PRESET`.
- **Validating presets inside `merge_config`:** errors would mix preset and file locations, and the built-in presets would be checked only when merged.
- **Checking `--preset-file` in `cli._resolve` as well as in storage:** the `preset:` key needs the same checks in storage. One implementation, with the origin passed as the hint.
- **`--preset` accepting a path when it looks like one:** reverses D-029's exit 2 for `--preset ../x` and makes a choice option free text. The user asked for a separate option.
- **Naming a preset file only when given on the command line:** a file from the config key would then be invisible in the summary, which the user asked for.
- **A did-you-mean suggestion for unknown keys:** useful but new wording machinery. The key name and the file already locate the typo.

## Test plan

Default suite (`not live and not browser`). Every failure asserts four things: the exit code, exactly one stderr line starting `dbtscope: error: `, no `Traceback`, and the absolute path plus the key or hint.

**`tests/unit/test_config.py`** (domain, pure):
- `check_preset` returns the same object (`is`) for a valid preset.
- Unknown key at the top level, in a rule (`kinds[0].colour`) and in `universe` (`universe.bogus`): `unknown key` with the location.
- Each `NOT_IN_PRESET` key gives its problem text.
- Wrong types are refused: `offline: "yes"`, `include_packages: 1`, `language: EN`, `select: 3`, `select: [1]`, `key_columns: 5`, `kinds: {key: x}` (a mapping, not a list), `universe: []`, `title: true`. `group_by: bogus` and a bad regex are refused through the inherited validators.
- The shorthands are accepted: `select: "fct_*"` and `title: 2024`.
- An empty dict is valid.
- `is_preset_path`, parametrised: `data_vault` gives False; `team.yml`, `TEAM.YAML`, `./team`, `conf/team`, `conf\team`, `/abs/team` and `team.yaml` give True.
- `merge_config` with `{"bogus": 1}` in the file still works (`dbt-erd.yml` stays lenient, regression).

**`tests/unit/test_project_files.py`:**
- **Every built-in preset is valid:** parametrised over `PRESETS.iterdir()` `*.yml`, `check_preset` on each file's raw YAML. `read_preset(name)` equals `yaml.safe_load` of the file (validation does not alter content).

  - a valid file gives its dict;

  - key `nope` gives the extended hint;
  - key `""` gives no preset;
  - precedence: file key beats preset key value, and the CLI preset beats the file's key;
  - `LoadedConfig.preset` is the name or the absolute path.
