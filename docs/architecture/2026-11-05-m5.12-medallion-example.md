# M5.12 — The example project as a medallion (design note)

Status: Accepted by the user on 2026-11-05 (supersedes the "star-schema marts in dbt groups" and "`group`, `access` and `meta` under `config:`" clauses of D-033 with D-047)

## Context

Request: restructure `examples/acme_retail/` (D-033) so that the dbtscope page shows a medallion architecture (Bronze / Silver / Gold) as clearly as the business domains, with domains and layers coming from the dbt project's own conventions (folder = layer, subfolder = schema = domain) instead of dbt groups and `meta.domain`, as in a real project the user showed. No change to `src/dbtscope/`.

Roadmap: new item M5.12 (free; M5.11 is the last used id).

Current state:

- `models/staging/<system>/` (18 `stg_*` views, schema `staging`), `models/raw_vault/<domain>/` (38 hubs, links, satellites, schema `raw_vault`, domain in `config.meta.domain`), `models/marts/<domain>/` (16 facts and dimensions, schema `marts`, `config.group` + `access: public`, 6 groups with owners in `models/marts/groups.yml`), `seeds/` (3), `snapshots/` (2, `target_schema='snapshots'`), sources `raw_<system>`.
- `dbt-erd.yml`: preset `data_vault` (`group_by: schema`), kinds, 7 domain rules (sources, staging, seeds, snapshots only), 4 layer rules (Sources, Staging, Raw vault, Marts).
- How dbtscope assigns a domain (`domain/universe.domain_of`): dbt group > `meta.domain` > first `domains` rule > `group_of(table, group_by)`. A domain's label and colour come from the `domains` rule **with the same key**, whether or not that rule matched the table (`universe._domains`, `configured.get(key)`). The layer is the first `layers` rule, or the first folder under `models/` when no layer is configured, ordered by `FLOW_PREFIXES`.
- dbt-duckdb's default `generate_schema_name` writes `<target schema>_<custom schema>`: today `main_raw_vault`, `main_marts` (the detail groups in `expected.json`).

## Chosen design

### Folders (moves only, file contents unchanged)

| Before | After | Notes |
|---|---|---|
| `models/staging/<system>/stg_*.sql` | `models/bronze_<system>/stg_*.sql` (erp, crm, web, billing, wms) | one folder per source system, no subfolder |
| `models/staging/sources.yml` | `models/bronze_<system>/sources.yml`, one per system, each holding the `raw_<system>` source of its folder | source names, tables, columns and tests unchanged, so source `unique_id`s are unchanged |
| `models/raw_vault/<domain>/*.sql` | `models/silver/<domain>/*.sql` | the domain folders already exist |
| `models/raw_vault/raw_vault.yml` | `models/silver/silver.yml` | minus every `config: {meta: {domain: …}}` block |
| `models/marts/<domain>/*.sql` | `models/gold/<domain>/*.sql` | |
| `models/marts/marts.yml` | `models/gold/gold.yml` | minus every `group:` and `access:` line (all were `public`, the default); `contract` stays under `config:` |
| `models/marts/groups.yml` | deleted | no more dbt groups, no owners |
| `seeds/`, `snapshots/` | unchanged | |

Model names, and so every `unique_id` (`model.acme_retail.<name>`, invariant 11), are unchanged: saved layouts and the tests' ids stay valid. Before moving, the developer checks that every vault model's folder equals its `meta.domain` and every mart's folder equals its `group` (the folder is the domain from now on); if one differs, the folder wins only if the user agrees, otherwise move the file to the folder of its current domain so that **every table keeps its domain key**.

### `dbt_project.yml`: schema = domain

```yaml
models:
  acme_retail:
    bronze_erp: {+materialized: view, +schema: erp}
    bronze_crm: {+materialized: view, +schema: crm}
    bronze_web: {+materialized: view, +schema: web}
    bronze_billing: {+materialized: view, +schema: billing}
    bronze_wms: {+materialized: view, +schema: wms}
    silver:
      +materialized: table
      sales: {+schema: sales}
      customer: {+schema: customer}
      product: {+schema: product}
      marketing: {+schema: marketing}
      finance: {+schema: finance}
      logistics: {+schema: logistics}
    gold:
      +materialized: table
      sales: {+schema: sales}
      # … the same six domains
```

The same schema name in `silver/<domain>` and `gold/<domain>` puts a domain's vault and marts in one constellation through `group_by: schema` (already set by the `data_vault` preset).

New file `macros/generate_schema_name.sql`, the widespread override that uses the custom schema as is (target schema when none):

```sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {{ custom_schema_name | trim if custom_schema_name is not none else target.schema }}
{%- endmacro %}
```

Why: without it dbt-duckdb names the schemas `main_sales`, … so the domain keys become `main_sales` (layout keys and rule keys change, labels would read `main_sales` without a rule). With it the keys stay `sales`, `customer`, … exactly as today, so the domain keys of every table, the domain rules' labels and colours and the layout file's `domains` keys are unchanged. `dbt parse` resolves schema names with the project's macro (no connection); dbt Fusion supports this override too. Bronze schemas are the system names (`erp`, …), mirroring the sources' `raw_<system>`; they never become domains because the domain rules place every bronze model first.

### `+database` per tier: not used

dbt-duckdb would parse a `+database: bronze` without connecting, and the `database:` selector could then drive layers. Rejected for the example: the path already says the tier, so it would be a second signal for the same thing; and a `dbt build` on the example would then need three `attach:` entries in `profiles.yml`, more noise in a file whose point is "no secret, nothing to configure". The README can mention that a project with one database per layer can write its layer rules as `database:bronze` instead of `path:`.

### `dbt-erd.yml`: as small as the conventions allow

- `preset: data_vault`, `title`, `language`, `view`, `select` and `kinds`: unchanged (the kinds name `fct_*` / `dim_*`, which the preset lacks).
- **Domains**: the 7 existing rules stay, with their keys, labels and colours. They now do two jobs, said in the comment: they place the tables that carry no domain in their schema (sources, bronze models, seeds, snapshots: organised by source system, not by domain), and they give every domain its label and colour (silver and gold tables take the key from their schema, the rule of that key labels it). The match lists are unchanged (they name tables, not paths). Rejected: one schema per domain for bronze models too (a `config(schema=…)` in each bronze file, or a `bronze_erp/<domain>/` split): per-file config, and it misrepresents bronze, which is per source system in a real medallion.
- **Layers**: explicit rules, because the default cannot give the medallion: with no layer rule each `bronze_<system>` folder is its own layer, and `bronze*`, `silver`, `gold` have no `FLOW_PREFIXES` entry, so they sort alphabetically at `UNRANKED` (bronze_billing … bronze_wms, gold, silver: Gold before Silver).

```yaml
layers:
  - {key: source, label: Sources, match: ["type:source"]}
  - {key: bronze, label: Bronze, match: ["path:models/bronze_*", "type:seed", "type:snapshot"]}
  - {key: silver, label: Silver, match: ["path:models/silver/*"]}
  - {key: gold, label: Gold, match: ["path:models/gold/*"]}
```

(`selectors.glob` is `fnmatch`, whose `*` also matches `/`.) Tiers:

- **Sources** keep their own first band: they are what lands from the systems, not built by dbt; a separate band shows the entry of the flow. Rejected: sources in Bronze (three bands exactly, but each bronze band would mix raw tables with the views that read them, and the layer filter could no longer hide the raw tables alone).
- **Seeds** in Bronze: reference data loaded as is, like a landed file.
- **Snapshots** in Bronze: they capture the history of a bronze model (`customers_snapshot` reads `stg_erp__customers`), before any modelling; as today, where they sat with staging.

Layer keys and labels change (`staging` → `bronze` "Bronze", `vault` → `silver` "Silver", `marts` → `gold` "Gold"); every table stays in the band of the same rank, so the universe layout is equivalent.

### What changes in the outputs

- Universe: same 95 tables, 7 domains (same keys, labels, colours), 58 relations, 110 lineage links; domain owners disappear (no group); layer bands and the Layers panel read Sources → Bronze → Silver → Gold.
- Detail: same 54 tables, kinds and relations; the group list becomes the six domain schemas (`sales`, `customer`, …, each holding its silver and gold tables) instead of `main_raw_vault` / `main_marts`.
- Untyped columns: unchanged (16, 13 keys).

No code, payload format, layout format or CLI change; the M3 reference pages (shop) are untouched.

### Errors

None new: the example either parses or the regeneration tool fails as today (`tools/example_manifest.py`). `dbt parse` must still emit no warning (an orphan `+schema` key for a folder that does not exist warns: every folder named in `dbt_project.yml` must exist).

## Rejected options

- **Keep dbt groups for gold** (owners demo): the user chose domains by convention; groups would also override the schema for gold only. The owner tooltip stays covered by the `shop` fixture's `sales_team` group (owner Ana).
- **Keep `meta.domain` on silver**: redundant with the schema, the opposite of "convention, not config".
- **Default `main_<schema>` names with rules keyed `main_sales`**: changes every domain key (layouts, tests, the docs' examples) and shows the adapter prefix in the payload.
- **`group_by: folder:2`** instead of schemas: would key domains `silver/sales` and `gold/sales` (two constellations per domain).
- **Adding `bronze` / `silver` / `gold` to `FLOW_PREFIXES`** so the default layers order them: a `src/` change (out of scope) and still one layer per `bronze_<system>` folder. Listed under "Later".
- **`+database` per tier**: see above.
