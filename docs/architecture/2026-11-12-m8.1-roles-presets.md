# M8.1 — Roles, complete presets, the large test project (design note)

Status: APPROVED FOR AUTONOMOUS MODE (the user asked for the whole of M8 to be built without stopping; every point the brief leaves open is settled below and recorded in D-058, D-059, D-060).

## Context

Request: give every kind an optional **role** that drives star size, name priority and the order of the Types list; make both built-in presets classify every table of a usual project (staging, dimensions, facts) and set default layers; add a generated 1,374-table Data Vault project to the tests. Roadmap M8.1, brief `docs/briefs/2026-11-12-m8-synthesis.md` § 5 (constraints § 4). It carries the vocabulary of M8.2 (parent of a descriptive table), M8.3 (main core tables of a card), M8.4 (source system = only technical tables) and M8.5 (skeleton = core and connector tables, in the detail).

Current state of the code:

- `domain/config.Rule` serves `kinds`, `domains` and `layers` alike (`key`, `label`, `color`, `match`). `merge_config` replaces lists: a `kinds` list in `dbt-erd.yml` replaces the preset's whole list; there is no merge by key today.
- `domain/universe._kinds` emits the configured kinds used, then the built-ins `TYPE_KINDS` (source, seed, snapshot) and `classify.OTHER`. `domain/detail.detail_data` emits configured kinds and `OTHER` only (a source in the detail is `other`).
- `render/assets/universe.js`: `starR(n) = min(14, 3 + 1.6·√DEG)`, `DEG` = relations + lineage of the table. So stars already vary by degree; the brief-universe-view § 3 sentence "all stars have the same size" was already out of date. Names compete by `labelScore` (degree weighted by the kind's position in `DATA.kinds`). The word `role` is used in `universe.js` for the **trajectory** (`roleOf` → `start | up | down`).
- `domain/universe.flow_rank` ranks a default layer (no `layers` rules) by folder-name prefix (`FLOW_PREFIXES`, minimum rank over matching prefixes). `raw` has rank 1 (staging), so a `raw_vault` folder ranks as staging today.
- Presets: `data_vault` has nine kinds, no staging / dimension / fact kind, no layers; `star_schema` has fact, dimension, bridge, no layers.

## Chosen design

### 1. Role on a kind rule (config)

- `domain/config.py`
  - `Role = Literal["core", "connector", "descriptive", "technical"]` and `ROLES` (the tuple of its values, in that order: also the order of the Types list). Declared here only, reused by `payload` and `classify`, like `Language`.
  - New `KindRule(Rule)`: one more field, `role: Role | None = None`. A `field_validator("role", mode="before")`: `None` or `""` → `None`; a string in `ROLES` → itself (case kept as written: no lower-casing, values are lower case); anything else → `ValueError(f"invalid role {value!r} ({in_words(ROLES)})")`. Message as D-041, through `validation_message`; storage adds the file and `; fix the file`:
    `config /p/dbt-erd.yml: kinds[2].role: invalid role 'hubs' (core, connector, descriptive or technical); fix the file`.
  - `Config.kinds: KindRuleList` (`tuple[KindRule, ...]`). `domains` and `layers` stay `Rule`: a `role` on a domain or layer rule of `dbt-erd.yml` is an unknown key, ignored (lenient file, invariant 9); in a preset it is an `unknown key` error (`PRESET_SETTINGS`, D-030).
  - New `PresetKindRule(KindRule)` with `PRESET_SETTINGS`; `Preset.kinds: tuple[PresetKindRule, ...]`.
  - `Config._kind_colors` unchanged (works on `KindRule`).
- **Merge rule.** Lists still replace lists (D-015 / D-030 unchanged). New private helper `config._inherit_roles(preset_kinds, file_kinds)`, called by `merge_config` on the raw dicts before validation when both values are lists: each file kind that is a mapping, has a `key` equal to a preset kind's `key` and has **no `role` key at all** receives that preset kind's `role` (when the preset kind has one). A file kind that writes `role: null` or `role: ""` keeps no role (it set one: none). A file kind whose key is not in the preset gets nothing. A malformed value (not a list, an item not a mapping) is passed on unchanged for validation to report. The preset's kinds that the file does not repeat are still dropped (list replacement), as today. A `--preset` on the command line goes through the same `merge_config`.
- **Built-in kinds.** `classify.BuiltinKind` gains `role: Role | None = None`. `TYPE_KINDS` source, seed, snapshot: `role="technical"`. `OTHER`: none.

### 2. Payload

- `payload.UniverseKind`: `key, label, color, role` — `role: Role | None = None`, **last key**. `payload.DetailKind`: `key, label, color, bg, role`, `role` last, same type and default (M8.5 needs it in the detail).
- Absence is JSON `null` (rejected: `""`, omitting the key — logic in `payload.py`, as D-048 rejected).
- No role on nodes or entities: the page reads `KIND[n.kind].role` (smallest payload, one fact in one place).
- `universe._kinds`: `UniverseKind(..., role=k.role)` for configured kinds, `t.role` for built-ins. `detail.detail_data`: `role=k.role`, `OTHER.role` (null). The order of `kinds` in both payloads is unchanged (config order, then built-ins, then `other`): the role order is applied by the page, so a payload without roles keeps its order.

**Expected diff of `tests/fixtures/m3-reference-pages/payloads/*.json`** (to be checked once by the developer, with a script, before `tests/reference_pages.py` regenerates them; the result written in `docs/progress.md`):

| Case | Diff of the payload |
|---|---|
| `none`, `fr`, `edge`, `layers_domains` | Each universe kind gains `,"role":…` as its last key: `source` → `"technical"`, `other` → `null`; each detail kind gains `,"role":null`. Nothing else. |
| `kinds` | Every universe and detail kind gains `,"role":null` (the user kinds `fact`, `dim`, `stage`, `src` have no role; `src` takes the sources, so no built-in `source` kind is used). Nothing else. |

Detail kinds gain roles. |

| offline twins | Same data as their CDN case. |

Every `expected.json` hash and size changes (assets change too). Rule for Done-when 3: the five cases with no preset differ by the `role` keys only.

### 3. Page, universe (`render/assets/universe.js`)

Python decides the role; the browser draws. Constants (all in `universe.js`, values set by the ui-designer):

| Constant | What | Proposal for the ui-designer |
|---|---|---|
| `ROLE_ORDER` | `['core', 'connector', 'descriptive', 'technical', null]`: the Types list order | brief, fixed |
| `ROLE_STAR` | radius factor by role; `null` and `connector` → 1 | core 1.35, descriptive 0.7, technical 0.7 |
| `STAR_MAX` | the cap of the degree radius, today the literal 14 (named, also used by `drawNames`' `rMax`, which must become the largest drawn radius, `STAR_MAX × max(ROLE_STAR)`) | 14 |
| `NAME_ORDER` | name priority by role: `core, connector, null, descriptive, technical` | fixed (below) |
| `OVERVIEW_K` | the scale below which only core names are offered (when the page has a core kind) | 0.6 (the "far" threshold of routes and band markers) |

- **Star size.** `starR(n) = min(STAR_MAX, 3 + 1.6·√DEG[n.i]) × (ROLE_STAR[role(n)] ?? 1)`, where `role(n) = KIND[n.kind].role`. The degree still sizes the star inside a role. `box(n)` reads `starR`, so reserved boxes follow (D-040 packing unchanged in its rules, smaller boxes for descriptive and technical tables).
- **Pages without roles** (no preset, no `role` key): user kinds and `other` are unchanged; **source, seed and snapshot stars shrink by `ROLE_STAR.technical`**, so their reserved boxes are lower (height `2r + 4 + label`, width rarely, since the label is usually wider) and the D-040 packing of constellations holding them is slightly tighter. Saved arrangements load unchanged (offsets from the centre; the de-overlap pass still runs around dragged tables). D-040's acceptance (fill or 15 % rule) is measured again on acme_retail and the 1,500-table payload; thresholds unchanged.
- **Names.** One helper `mainTables(members)`: the core tables of a constellation ordered by number of **relations** (business relations of the payload, both ends, unfiltered, so the names do not change with the Links selector), then `DEG`, then name, then `unique_id`. Computed in `layout()` per constellation; `MAIN` maps a table to its rank in its constellation (0 = main). M8.3 reuses `mainTables` for the 3–5 names of a card.
  - The relation count is **computed in the browser from `DATA.relations`**, not carried by the payload: it is arithmetic on data the payload already holds (as `DEG` is today), it depends on the grouping (domain or layer constellation) which only the page knows (D-048), and 1,374 more integers would duplicate `DEG`'s source. "Python decides" covers classifications (role, parent, source system), not counts of embedded links.
  - Order of candidates (`orderLabels`): trajectory tables, the hovered table, then by `NAME_ORDER` of the role; inside `core` by `MAIN` rank (every constellation's main table before any second one), then `labelScore`; inside the other roles by `labelScore` as today.
  - **At overview** (`k < OVERVIEW_K`) and when `DATA.kinds` has a `core` kind: ordinary candidates are the core tables only (trajectory and hovered names still compete). The collision rules of D-040 apply unchanged. So the names at Fit are core tables with the most relations, never an arbitrary one. A page with no core kind keeps today's candidates (technical last).
  - Why a separate `NAME_ORDER`: with no roles, putting `technical` before `null` (as in the Types list) would push source names ahead of every user kind; for names, plumbing is least worth the room.
- **Types list.** `refreshPanel` lists `DATA.kinds` stably sorted by `ROLE_ORDER` (then payload order). On a page without roles this moves Source, Seed, Snapshot above the user kinds and `other` stays last. No group headings in M8.1 (ui-designer may add them, with strings in en and fr).
- **Glossary clean-up.** The trajectory's `roleOf` / `role` in `universe.js` become `sideOf` / `side` (`start | up | down`), so "role" means one thing (D-027). `flow.js` and `page.html` only use the ARIA `role` attribute: untouched.
- **Test hooks.** `geometry()` gains `r` (drawn star radius, world px) per table; the handle gains `drawnNames()` (the indices of table names drawn in the last frame).

### 4. Presets

- **Steps of the data flow, one list.** New module `domain/steps.py` (moved out of `universe.py` so `selectors` can use it without an import cycle `universe → classify → selectors`):
  - `STEPS`: the ordered named steps with their folder-name prefixes; the rank is the index:
    `source` (`source`), `staging` (`raw`, `stg`, `staging`, `base`), `reference` (`seed`, `ref`), `intermediate` (`int`, `intermediate`, `vault`, `snapshot`, **`raw_vault`, `business_vault`**), `product` (`dp`, `mart`, `marts`, `product`, **`data_product`**), `report` (`report`, `expo`).
  - `FLOW_PREFIXES` (derived from `STEPS`: `(prefix, rank)`), `UNRANKED` (4.5), `default_layer(table)` (was `universe._default_layer`), `flow_rank(key)` and new `step_of(key)` (the step name, `""` when unranked). Both use the **longest** matching prefix (was the minimum rank): identical for every existing prefix (no existing prefix is a prefix of another with a different rank), and it lets `raw_vault` beat `raw`.
  - Page change for projects without `layers` rules: a `raw_vault`, `business_vault` or `data_product*` folder now ranks 3 / 3 / 4 (was 1 / 4.5 / 4.5). Only the order of the Layers list and of the bands changes.
- **New selector field `step:`** (`domain/selectors.py`): `step:<glob>` matches the step of the table's default layer (`step_of(default_layer(table))`), e.g. `step:intermediate`. Computed like `tag`, so `FIELDS = {*ATTRIBUTES, "tag", "step"}` and the unknown-field error lists it. Usable by users too (documented with the selectors). Old files cannot hold it (it was an error), so the format is only extended.
- **Default layers in the presets**, written with `step:` (labels are preset data, so nothing Data-Vault-specific enters the code):
  - `data_vault`:
    `{key: sources, label: Sources, match: ["step:source"]}`,
    `{key: staging, label: Staging, match: ["step:staging", "step:reference", "type:seed", "type:snapshot"]}`,
    `{key: raw_vault, label: Raw vault, match: ["step:intermediate"]}`,
    `{key: data_products, label: Data products, match: ["step:product", "step:report"]}`.
  - `star_schema`: same `sources`, `staging`; `{key: intermediate, label: Intermediate, match: ["step:intermediate"]}`; `{key: marts, label: Marts, match: ["step:product", "step:report"]}`.
  - Snapshots go to Staging (`type:snapshot` before the intermediate rule; first match wins), as the example does with Bronze. A folder with no step goes to the catch-all `other` layer. A project's own `layers` replace the preset's (list replacement); `layers: []` brings the folder layers back (documented).
- **Kinds and roles** (`select`, `exclude`, `key_columns`, `group_by`, `title` unchanged):
  - `data_vault`, in this order: `staging` (**first**, so a `stg_*_hub` staging model is never a hub), `hub` core, `link` connector, `nhlink` connector, `sal` connector, `sat` descriptive, `refhub` core, `refsat` descriptive, `pit` descriptive, `bridge` connector, `dim` core, `fact` core. New: `{key: staging, label: Staging, role: technical, match: ["stg_*"]}`, `{key: dim, label: Dimension, role: core, match: ["dim_*"]}`, `{key: fact, label: Fact, role: core, match: ["fct_*"]}` (keys and labels as `star_schema` and the example, so one word per concept).
  - `star_schema`: `staging` first (technical, `stg_*`), `fact` core, `dim` core, `bridge` **connector** (the brief left the star-schema connector empty: a bridge relates a fact to a dimension, as in Data Vault).
- **Colours of the new kinds.** Requirements: the colour itself reaches 3:1 on `#f5f6f8` (so no D-042 outline is needed), any text colour is chosen by D-037; at least 12 CIEDE2000 from every other kind colour of its preset, from the built-in kinds and `OTHER` (`tests/colours.ciede2000`), and from the seed (`test_the_seed_colour_stands_apart_from_every_shipped_colour` already reads every preset colour). The developer takes the first candidate that passes and reports the distances (palette distances reported, not required):
  - staging (both presets, same colour): `#a08497`, then `#9c8a7a`, `#8f9a7c`;
  - DV fact: `#a2337a`, then `#b83280`, `#c2185b` (`#d9822b`, star schema's fact, is about 11 from `pit #b5651d`: refused);
  - DV dimension: `#0b8fb3`, then `#0e9bbd`, `#4aa3df` (`#2f6fb5`, star schema's dimension, is the DV hub).
  - Existing colours do not change.
- **acme_retail.** `examples/acme_retail/dbt-erd.yml` drops its five kind rules (`hub`, `link`, `sat` equal the preset's; `fact`, `dim` now come from the preset, with the preset's colours), keeps `select`, `domains`, `layers`. Effects: the 18 `stg_*` models become Staging (Other disappears from the example); fact and dimension take the DV preset colours; the detail kinds keep their labels and counts. `tests/fixtures/acme_retail/expected.json` gains `universe.kinds` (`Staging 18, Source 18, Seed 3, Snapshot 2, Hub 13, Link 12, Satellite 13, Fact 8, Dimension 8`; no `Other`); the other counts are unchanged; `notes.md`, the user-guide walkthrough and its excerpts (checked by `tests/unit/test_docs.py`) follow. The manifest is not regenerated (no dbt file changes).

### Error handling

Only one new failure: an invalid `role` (one line, exit 1, nothing written). An invalid `step:` value is never an error (a glob that matches nothing). Unknown `role` on a domain or layer rule of `dbt-erd.yml` is ignored; in a preset it is `unknown key`.

## Rejected options

- **Merge kinds by key** (a file kind updates the preset kind of the same key, others kept): changes the list semantics of D-015 / D-030 for every existing file. Only the role is inherited.
- **Role on `Rule`** (shared by domains and layers): a preset could carry a meaningless `role` on a domain rule silently.
- **Role on every node / entity**: duplicates the kind's role 1,374 times.
- **Kinds sorted by role in the payload**: changes the payload order of pages with no role (Done-when 3).
- **Relation counts in the payload**: see § 3; grouping-dependent and already derivable.
- **Preset layer rules with `path:` globs in the YAML**: a second list of folder names next to `FLOW_PREFIXES` (invariant 2), and labels would still be needed. **Layer rules generated in code from `FLOW_PREFIXES`**: labels like "Raw vault" are Data Vault data, not code. **A new `layers: default` value**: a second meaning for a list key.
- **Medallion prefixes (`bronze`, `silver`, `gold`)**: a roadmap "Later" item, out of M8 (brief § 4).
- **Fact `#d9822b` and dimension `#2f6fb5` in `data_vault`**: too near `pit` and equal to `hub`.
- **A committed large manifest**: about 5 MB raw; a generator in code is reviewable and deterministic, as `big_manifest`.

## UI design

Task: find the structure of a large vault at a glance (which tables are the business entities) and still read a small project as before. Decision served: where to zoom next. No new control, panel or step; only sizes, name priority and list order change.

### Constants (`universe.js`, paste as is; they replace the proposals of § 3)

```js
const ROLE_ORDER = ['core', 'connector', 'descriptive', 'technical', null];   // Types list
const NAME_ORDER = ['core', 'connector', null, 'descriptive', 'technical'];   // name priority
const ROLE_STAR = { core: 1.35, descriptive: 0.75, technical: 0.75 };          // connector and none: 1
const STAR_MAX = 14, STAR_MIN = 2.5;   // degree radius cap before the factor; floor after it (world px)
const OVERVIEW_K = 0.6;                // = the `far` threshold of drawStar, routes and band markers
const OVERVIEW_NAMES = 3;              // core names offered per constellation below OVERVIEW_K
```

### Star size

`starR(n) = Math.max(STAR_MIN, Math.min(STAR_MAX, 3 + 1.6 * Math.sqrt(DEG[n.i])) * (ROLE_STAR[role(n)] ?? 1))`. The degree radius spans 3 (degree 0) to 14 (degree 48 and more). Resulting radii in px at scale 1:

| Role | Factor | Radius range | Diameter range |
|---|---|---|---|
| core | 1.35 | 4.05 to 18.9 | 8 to 38 |
| connector, none | 1 | 3 to 14 | 6 to 28 |
| descriptive, technical | 0.75 | 2.5 (floor, from 2.25) to 10.5 | 5 to 21 |

- The smallest star is 5 px across, exactly the floor `drawStar` already enforces for a star seen from afar (`2.5 / k`), so no smaller mark than today exists; the floor is now in `starR`, so `box` and the drawing agree. The D-042 rule is unchanged: fill in the kind colour, 1 px outline in `CONTRAST.edge` (3:1) when the colour falls short, so a 5 px mark is still a 3:1 mark. Ratio core : descriptive at equal degree is 1.8, clearly visible.
- Hit-test is independent of the radius (`pickAt`: 8 px or `8 / k`, nearest star); a small star stays as easy to hit as before. Touch: unchanged (the 44 px rule concerns controls).
- **Reserved boxes follow the factor** (`box` reads `starR`): descriptive and technical tables take less room, core more (height `2r + 4 + label`). D-040 rules unchanged; `drawNames` `rMax = STAR_MAX * ROLE_STAR.core * k` (floored at 2.5), `rad(n)` uses the new `starR`; `drawStar`'s own floor `Math.max(starR(n), (role ? 3 : 2.5) / k)` is unchanged.

### Names

- Candidate order (`orderLabels`): (1) trajectory tables by distance, (2) the hovered table, (3) ordinary names by `NAME_ORDER` of the role; inside `core` by `MAIN` rank (every constellation's first before any second), then `labelScore`; inside the other roles by `labelScore`. Within one role, tables without a role keep today's order.
- **At overview** (`k < OVERVIEW_K`), when `DATA.kinds` has a `core` kind: ordinary candidates are the core tables with `MAIN < OVERVIEW_NAMES` (at most 3 per constellation, the 3 with most relations). Trajectory and hovered names still compete. From `OVERVIEW_K` up every table competes by the order above. A constellation with no core table (for instance the Sources layer in layer mode) shows no table name at overview; its own name is still drawn. Collision rules of D-040 apply unchanged, so fewer than 3 may show.
- The 3 matches the "3 to 5 names" of the M8.3 cards (they take the 5 of `mainTables`; M8.3 decides below `FAR = 0.5`, this rule only governs names). Page with no core kind: today's candidates, no cap.
- Name font weight rule `strong` (`labelScore >= 10`) unchanged.

### Types list

Sorted by `ROLE_ORDER`, stable. No headings, no separators (a heading row would be a non-checkbox row in a list of checkboxes and cost height at 360 px). Each kind row with a role gets a tooltip (`title`) `Role: core` / `Rôle\u00a0: centrale`, built as `${T.role}${L.colon}${T.roles[role]}`; a kind with no role keeps its label as title. The role is therefore never conveyed by size or order alone.

| Key | English | French |
|---|---|---|
| `T.role` | role | rôle |
| `T.roles.core` | core | centrale |
| `T.roles.connector` | connector | de liaison |
| `T.roles.descriptive` | descriptive | descriptive |
| `T.roles.technical` | technical | technique |

(In French the colon is written `\u00a0:` through `L.colon`, D-039.)
