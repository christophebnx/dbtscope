# M9.3 — Flow view: the paths between two tables (design note)

Status: APPROVED FOR AUTONOMOUS MODE. The user approved this item of `docs/roadmap.md` § Later on 2026-11-12 ("Flow view: the paths between two chosen tables"). D-060 is new and refines D-036 (the flow shows a trajectory, or now the paths between its start and a target); nothing is superseded. No payload, layout, localStorage or CLI change. The ui-designer designs the points marked **[UI]**. Order of M8: see `2026-11-12-m9.2-table-link.md` (this is the second of three; independent of M9.2).

## Context

**Request.** Choose a start and a target table; draw every table on a directed lineage path between them, left to right like the flow (D-036), with a cap like the flow's 150 tables.

**Current code.** `flow.js startFlow` draws the trajectory of `st.start` at `st.direction` / `st.depth`: `prepare()` runs `trajectory()` (`common.js`) at full depth, reduces the depth to fit `FLOW_MAX` = 150 (or cuts level 1), then `trajectoryEdges`, `flowRanks` and `buildDot`. Depth labels come from the `up` / `down` distance maps; the start has its ring (M5.11). A click on a table recentres. `state()` is the test hook. The universe payload holds every lineage pair of the universe scope.

## Chosen design

### 1. Where: a target in the flow view

The paths are a mode of the flow view, not a new view: the flow already has the left-to-right drawing, the columns, the cap, the tooltip, the export and the overlay that leaves the universe untouched (D-036). The start is the flow's start; the user adds a **target**.

- **Target field [UI]:** in `#f-bar`, after Depth, a labelled input "Paths to" / "Chemins vers" (`#f-to`, `list="f-to-names"`), with a datalist of the tables that have a lineage path to or from the start (its whole trajectory, both directions, every level), by name. A name shared by two of them gets its domain label after it (`orders · Sales`) in both options; options are built with DOM calls (untrusted names). Picking or typing an exact option (case-insensitive) and confirming (`change`, Enter) enters the paths mode. A clear button `#f-to-clear` ("×", title "Back to the flow of <start>") leaves it.
- **No other entry point** in M9.3: the universe's trajectory bar keeps **Flow** only. The start is chosen as today (a trajectory, then Flow; or a recentre in the flow).

### 2. Which tables (`common.js lineagePaths`)

```js
// lineage: [[child, parent]]; start, target: indices.
// -> { up: Map(index -> distance from start), down: Map(...), toTarget: Map(index -> distance to target) }
// The tables on a directed lineage path between start and target, target included, on the target's side:
// down when the target is downstream of the start, up when it is upstream; both empty when no path.
function lineagePaths(lineage, start, target) { ... }
```

- Two traversals with the existing `trajectory()` at depth `Infinity`: from the start (both directions), and from the target towards the start (`up` when the target is downstream, `down` when upstream). A table is kept when it is reached by both; the target itself is kept. A target on both sides (a cycle of a malformed manifest) is taken downstream. O(V + E), never loops (the `seen` set of `trajectory`).
- **Why it is exactly the paths:** a table reached from the start and reaching the target lies on a start → target path, and every table of such a path is reached by both. Each lineage edge between two kept tables lies on a path, so `trajectoryEdges(lineage, start, up, down)` on the kept maps returns exactly the drawn edges, tagged `down` (solid orange) or `up` (dashed violet) as in the trajectory.
- **Distances** are the shortest from the start (the BFS of `trajectory`), so the depth labels read as in the flow: `+n` when the target is downstream, `−n` when upstream. For a kept table the shortest start path stays inside the kept set, so the label is also its shortest distance along the drawn paths.
- **Direction** is decided by the data, not by the user: the title always reads from the upstream end to the downstream end **[UI]**.

`flow.js prepare()` takes `lineagePaths` instead of `trajectory` when `st.target` is set; `trajectoryEdges`, `flowRanks`, `buildDot`, `header`, the ring and the export run unchanged on its maps. Columns: `flowRanks` as today, so the start and the target are the two ends and every edge goes left to right.

### 3. The cap (`FLOW_MAX`, unchanged at 150)

The flow's depth reduction does not fit paths (a level cut leaves the target unreachable). Instead, with `len(x) = distance from the start + toTarget(x)` (the length of the shortest path through `x`):

1. **All paths** when the kept tables, start included, number `≤ FLOW_MAX`.
2. Else **paths of at most `L` steps**: keep the tables with `len(x) ≤ L`, `L` the largest value `≥` the shortest path length that fits. The kept set stays connected from start to target: every table on a shortest start → `x` or `x` → target path has `len ≤ len(x)`. Message `capLength`.
3. Else (the shortest paths alone hold more than `FLOW_MAX` tables, a lattice) **one shortest path**: from the start, each step to the next table with `toTarget` one less, the first in the flow's `byPlace` order (domain label, then name), so it is deterministic. Message `capOne`. A single path longer than `FLOW_MAX − 1` steps is cut to its first `FLOW_MAX` tables with the same message (no manifest has such a chain; it only must not hang).

Budgets as D-036: preparation under 100 ms, render under 5 s on the 1,500-table payload.

### 4. Behaviour

- **Header in paths mode [UI]:** the title becomes "Paths from" + the upstream end + "to" + the downstream end ("Chemins de … à …"); the start keeps its button (`#f-start`, locate start, M5.11), the target is plain text with its kind dot. **Direction** and **Depth** are hidden (they do not apply) and come back with their values when the mode is left. Counts: `plural(total, L.tables)` + " · " + the path lengths ("paths of 4 to 6 steps", or "paths of 4 steps" when all are equal); the cap message when capped. The Domains list as today.
- **Target mark [UI]:** the target node shows the word **target** / **cible** after its depth (`+4 · target`) and a 3 px dark dashed frame, so it is found without colour; the start keeps its frame, label and ring. The Domains list legend gains a "target" row. The ui-designer may refine the mark (it must stay distinct from the start's).
- **Recentre:** a click (or Enter / Space) on a table leaves the paths mode and shows the flow of that table with the flow's direction and depth, as today; the target field empties. The tooltip's action line stays "Click: show its flow".
- **Clear:** `#f-to-clear`, or emptying the field and confirming, returns to the flow of the start with its direction and depth.
- **Esc:** unchanged rules (Domains list first, then the flow closes); on `#f-to` it belongs to the field and its list, as on the universe search box.
- **Live region:** "Paths from A to B: 9 tables · paths of 4 to 6 steps." (+ the cap message).
- **Nothing saved** (D-013); the universe trajectory and, after M9.2, the page link never change.
- **Export:** unchanged, `<title>-flow.png|svg`.

## Rejected options

- **A separate paths view or tab:** it would duplicate the flow's drawing, cap, tooltip, export and overlay (invariant 2).
- **Picking the target by clicking in the flow** (shift-click, a mode toggle): hidden gestures, no keyboard path; the flow only holds the start's trajectory anyway, which is exactly the datalist.
- **Picking start and target in the universe** (a second click mode): a new interaction model on the canvas for one feature; the trajectory already chooses the start.
- **Undirected paths** (through relations or in both directions at once): lineage only, up / down has meaning only along lineage (D-018).
- **Reducing depth as the flow does:** cuts the target off; path length keeps start and target connected.
- **Counting paths:** their number grows exponentially in a vault; the lengths say more.
- **Shortest paths only by default:** hides the alternative routes the user is asking about.
- **The target in the page link** (`#table=…&to=…`): M9.2 freezes one key; a later decision can add it, the parser ignores unknown keys.

### Decision D-060 (proposed; appended to `docs/decisions.md` by the documentation step)

> **D-060 — The flow view shows the lineage paths between its start and a chosen target.**
> Asked by the user on 2026-11-12 (M9.3, design note `docs/architecture/2026-11-12-m9.3-flow-paths.md`). In the flow view, a **Paths to** field lists the tables of the start's whole trajectory; choosing one draws only the tables on a directed lineage path between the start and that target (reached from the upstream end and reaching the downstream end), with every lineage edge between them, laid out by `flowRanks` as the flow (D-036), from the upstream end on the left to the downstream end on the right; the direction follows the data. Depth labels are shortest distances from the start; the target is marked with a word and a dashed frame. Direction and depth do not apply and are hidden. A click on a table, or the clear button, returns to a trajectory flow. Nothing is saved, the universe trajectory never moves, no payload change. Refines D-036 (what the flow shows; its overlay, columns, cap value, export and saving rules hold) and follows D-018 (lineage only). Rejected: a separate view, picking the target on the canvas, undirected paths, depth reduction for paths, counting paths, shortest paths only, the target in the page link.

### Default suite (Python)

### Browser (`tests/browser/test_flow_paths.py`, marker `browser`)

1. **`lineagePaths` pure checks** (`page.evaluate`): a chain; a diamond (both branches kept); a table reached from the start that does not reach the target is left out; a target upstream (maps on `up`); unrelated tables (both maps empty); a cycle `[[0,1],[1,0]]` returns and does not hang.
2. **Oracle on acme.** For a source table of the example and `fct_orders`: the drawn members equal `descendants(source) ∩ ancestors(fct_orders) ∪ {both}`, computed in Python from the payload's `lineage` (independent of the page code); `state().target` is the target id; every edge of `state().edges` has both ends in the members.
3. **Left to right.** Every edge's parent node centre x < child node centre x; the start has the smallest rank and the target the largest (target downstream), and the reverse when the target is upstream (labels `−n`).
4. **Labels and marks.** The target node text holds "target" ("cible" in fr) and its distance; the start holds "start"; the Domains list has a target row.
5. **Datalist.** Lists exactly the names of the start's whole trajectory; two members with one name get their domain labels; a hostile name (`a"b\c<d>&e{f}`) appears as text, no injection.
6. **Cap.** On a synthetic payload: (a) a ladder with more than 150 tables on paths of different lengths: `capKind == 'length'`, members `≤ FLOW_MAX`, start and target drawn and connected (every member reachable from the start along drawn edges and reaching the target); (b) a lattice whose shortest paths alone exceed 150: `capKind == 'one'`, members form one chain from start to target. Both show `#f-cap`.
7. **Performance** (the 1,500-table payload of `test_trajectory_perf.py`): paths from the hub's deepest source to a mart, `prepareMs` < 100 (median of 5), render to export-enabled < 5 s.
8. **Leaving.** Recentre on a member: `state().target` is `null`, the selects are shown with their values, the field is empty; clear button: same, start unchanged; the universe's `trajectoryState()` and `camera()` unchanged throughout; `Esc` in `#f-to` does not close the flow.
9. **Export.** SVG download `<title>-flow.svg` holds the target's name and the start's.
10. **Languages, sizes.** fr strings, no `undefined`; 360 × 800: `scroll_width() <= 360` in paths mode; coarse pointer: `#f-to` and `#f-to-clear` are 44 px.

### Task and decision

The user knows two tables and asks "how does the data of A reach B, and through what?". Decision: "which tables do I have to check between them, and is there more than one route?" The answer must read left to right, show both ends without colour alone, and say how many steps.

### Components

- **`#f-to`**: native `input type="text"` with a visible `label` "Paths to" (not a placeholder), `list="f-to-names"`, `autocomplete="off"`, placeholder "table name" ("nom de table"). Width 14 rem on desktop, full row at 360 px. Title `pathsToTitle`.
- **Datalist options**, by name, sorted by name (`localeCompare`); a name shared by two tables carries its domain label on both (`orders · Sales`), the option `value` being that exact text. The start is not offered. Built with DOM calls. Native filtering as the browser does it (hundreds of names are fine; the field is for those who know the name, like the universe search box).
- **Entering:** exact option text, case-insensitive, confirmed with `change` or Enter. Nothing happens while typing.
- **Invalid text** on confirm (not an option, or the start's own name): the paths mode is not entered, the field gets `aria-invalid="true"` and a message `#f-to-err` (`aria-describedby`, also `role="status"`) right under it in `--fg` on the surface with a 1 px accent-free border: "No table of this flow is called x" / "Aucune table de ce flux ne s'appelle x" (`noTarget`, x by `textContent`; for the start: "This is the start table" / "C'est la table de départ", `isStart`). It clears on the next input.
- **`#f-to-clear`**: a `button` labelled "×" with `aria-label` and title `clearTarget(start)`; shown only in paths mode, right of the field. Focus goes to the field after clearing.
- **Header in paths mode:** "Paths from" + upstream end + "to" + downstream end. The start always keeps its button (`#f-start`, locate); the target is plain text with its kind dot. When the target is upstream, the target comes first: "Paths from (o) raw_orders to [(o) fct_orders]" with the start button on the right. Direction and Depth get the `hidden` attribute (out of tab order and of the accessibility tree) and return with their values on leaving.
- **Target mark (resolves § 4):** the node reads `+4 · target` ("cible"; `−3 · target` upstream), and has a 3 px dashed frame in the text colour `#1f2933` (3 px solid for the start, which also keeps its ring and glow). Dashed versus solid, plus the word, separate the two ends without colour. No ring or glow on the target: the start remains the one thing found at a glance, the target is found by its word and sits at the far column. Contrast: the frame is 14:1 on white (D-042 needs 3:1); the label is node text, 4.5:1 as the depth labels.
- **Domains list legend:** a row "target" under "start" with a small dashed dark square (the same 1.5 px dashes as the frame), start's swatch unchanged (double frame).
- **Counts:** `plural(total, L.tables)` · `lengths(a, b)`. Cap message in `#f-cap`, the flow's existing element and style.
- **Live region:** "Paths from A to B: 9 tables · paths of 4 to 6 steps." plus the cap message; on leaving, "Flow of A: …" as today.

### Keyboard and focus
