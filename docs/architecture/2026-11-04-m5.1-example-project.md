# M5.1 — Example project `acme_retail` and tests on a real manifest (design note)

Status: DONE (built, tested and reviewed on 2026-11-04). The user asked for this on 2026-11-04. No documented decision is superseded. No released format changes. No page or CLI change. One new decision, D-033 (§ 7), sets a new test policy. If the compressed manifest is over 300 kB (§ 3), stop and ask the user.

## Context

Request: add the fake dbt project `acme_retail` to the repository as a demo and as test input. Test dbtscope on its real `dbt parse` manifest without needing dbt in the default run. Document how to install from the private repository and how to try the example. Roadmap: M5.1 (new).

Current state:
- Every test input is the synthetic `shop` manifest, built by hand in `tests/conftest.shop_manifest`. It has 6 tables and every column is typed. Real dbt manifests differ, and that let the M4.4 bug through: untyped columns broke the detail view.
- The project was generated in the session scratchpad by a one-off `generate.py`. It has 5 source systems (18 sources), 18 staging models, a Data Vault (13 hubs, 13 satellites, 12 links, `meta.domain` under `config:`), and 16 star-schema marts in 6 dbt groups with owners (`group` / `access` under `config:`). Relations come from `relationships` tests (`arguments:` form) and from `foreign_key` constraints (enforced contracts on `fct_orders` and `fct_order_lines`). There are 3 seeds, 2 snapshots and a `dbt-erd.yml` (preset `data_vault`, kinds, domains, layers). Its manifest (dbt-core 1.12.6 + dbt-duckdb 1.11.1) is 1.2 MB. The user ran it with dbt Fusion on macOS. Fusion rejects top-level `group` / `access` / `meta`, so they stay under `config:` in block style.
- Every column of the generated project that the detail view shows is typed. Only source columns, which the universe shows, have no type. So the example does not cover M4.4 as generated (§ 1).

## Chosen design

### 1. The example project: `examples/acme_retail/`, plain files, no generator

The generated files are committed as plain files and edited by hand from now on. The generator is **not** committed.
- The files are short and readable YAML / SQL. A dbt user changes them like any dbt project.
- A committed generator would need a drift test (files == generator output) and a second place to edit. That is two implementations of one fact (invariant 2).

Changes compared with the scratchpad output:
- **Untyped columns on purpose (M4.4 coverage).**
  - In `models/raw_vault/raw_vault.yml`, every satellite gets a second column `hd_<hub>`, with `description: Hash diff of the descriptive attributes` and **no** `data_type`. That makes 13 untyped columns. They match `key_columns` `^(hk_|hd_)` of the `data_vault` preset, so they are drawn in the default "keys" mode of the detail view.
  - In `models/marts/marts.yml`, three columns of marts **without** an enforced contract lose their `data_type`: `dim_campaign.channel`, `dim_carrier.service_level` and `fct_web_sessions.page_views`. They are drawn in "all columns" mode.
  - The contract marts (`fct_orders`, `fct_order_lines`) keep every type, because dbt requires them under an enforced contract.
  - The SQL files do not change.
- **Removed:** `target/`, `logs/`, `.user.yml`, any `*.duckdb`.
- **`.gitignore` of the example:** add `.user.yml`. It already lists `target/`, `logs/`, `dbt_packages/`, `erd_output/` and `*.duckdb`. The root `.gitignore` also ignores `target/` and `*.log`.
- **`README.md` of the example:**
  - Commands from the repository root: `dbtscope --project-dir examples/acme_retail`.
  - Install dbt with `uv tool install dbt-core --with dbt-duckdb`.
  - Say that `profiles.yml` holds no secret (a local duckdb path that is never opened by `dbt parse`).
  - Say that `group`, `access` and `meta` stay under `config:` in block style, for dbt Fusion.
  - Say how to regenerate the test manifest (§ 3).
- **Unchanged:** `dbt_project.yml`, `profiles.yml`, `dbt-erd.yml`, sources, seeds, snapshots, groups.

### 2. Real manifest in the default run: one gzip-compressed copy

Commit `tests/fixtures/acme_retail/manifest.json.gz`: the manifest exactly as `dbt parse` wrote it, compressed with `gzip` level 9 and `mtime=0`. Measured: 103,642 bytes (1,199,888 raw). The tests decompress it into the `target/manifest.json` of a temporary copy of the example. The CLI then runs with `--no-parse`, as a user without dbt would.

Why a full real manifest rather than a trimmed one: the point is the shape dbt really writes. That covers unknown fields ignored by `manifest_schema.INPUT`, `config.meta` vs `meta`, `group` under `config`, `arguments:` tests, constraints, seeds and snapshots. Trimming would drop exactly that, and the trimmer would depend on `manifest_schema`.

`.gitattributes`: add `*.gz binary`.

`tests/fixtures/acme_retail/` follows `tests/fixtures/README.md`:
- `manifest.json.gz`: the input.
- `expected.json`: `{"format": 1, "synthetic": true, …}`, holding the expected counts of § 6.
- `notes.md`: what the fixture covers, how it is regenerated, and the dbt versions used.

### 3. Regenerating the manifest: `tools/example_manifest.py`

```
uv run python tools/example_manifest.py --dbt <dbt with dbt-duckdb>
```

- `parse(dbt: str, workdir: Path) -> bytes` does the following:
  1. Copies `examples/acme_retail` into `workdir` (`shutil.copytree`).
  2. Sets `DBT_SEND_ANONYMOUS_USAGE_STATS=false` and `DO_NOT_TRACK=1` in the environment, so dbt calls nobody (invariant 5).
  3. Runs `dbtscope.cli.main(["--project-dir", workdir, "--dbt", dbt, "--no-open", "-o", workdir/"erd_output"/"erd.html"])` and raises if the exit code is not 0.
  4. Returns `workdir/target/manifest.json` as bytes.

  This reuses `cli._dbt_parse` through the public entry point: `dbt parse` is run in exactly one place (invariant 2). It also proves the real-dbt path end to end. The copy keeps `target/` and `logs/` out of the repository.
- `main(argv)`:
  1. `parse` into a `TemporaryDirectory`.
  2. `gzip.compress(data, compresslevel=9, mtime=0)`.
  3. Refuses (exit 1, one line) if the result is over 300 kB. A larger fixture needs the user's approval.
  4. Writes the file with `storage/files.atomic_write` (invariant 3).
  5. Prints the path, the raw size and the compressed size.
- argparse, like `tools/vendor_libraries.py`. `--dbt` defaults to `dbt`.
- To run it in this session: `/tmp/claude-0/-home-user-dbtscope/dcc6f8fd-e154-586a-995f-dff8243b2c5f/scratchpad/m42-sandbox/.venv/bin/dbt` (dbt-core 1.12.6, dbt-duckdb 1.11.1). Generate the manifest **after** the § 1 edits.

### 4. Is the committed manifest still the example's? An opt-in check, `DBTSCOPE_DBT`

`test_committed_manifest_matches_the_example` runs only when the environment variable `DBTSCOPE_DBT` names a dbt executable with dbt-duckdb (a path or a name on `PATH`). Otherwise it is skipped, with the reason `set DBTSCOPE_DBT to a dbt with dbt-duckdb`. This follows the precedent of `DBTSCOPE_CHROMIUM` (D-019).
- It calls `tools/example_manifest.parse` (through `conftest.load_script`).
- It reads both manifests with `storage/project_files.read_manifest`.
- It compares the models, not the bytes: `tables` (dict), `groups` and `root` must be equal, and `set(relations)` and `set(lineage)` must be equal. Bytes differ on every run (`generated_at`, `invocation_id`, the temporary root path).

Why an environment variable and no marker: the documented default command passes `-m "not live and not browser"` explicitly, which overrides `addopts`. A `dbt` marker excluded only by `addopts` would therefore run in every default run on a machine with dbt on `PATH`. The alternative is to edit that command in `CLAUDE.md`, the README, `ci.yml`, `tester.md` and the roadmap. An explicit variable needs no command change and never runs by accident. CI does not set it.

### 5. Test helpers (D-028: plain functions, fixtures only for pytest machinery)

- **`tests/conftest.py`**
  - Constants `EXAMPLE` (`<repo>/examples/acme_retail`) and `EXAMPLE_MANIFEST` (`tests/fixtures/acme_retail/manifest.json.gz`).
  - `write_example(folder: Path) -> Path`: `copytree(EXAMPLE, folder)`, then `write_manifest(folder, gzip.decompress(EXAMPLE_MANIFEST.read_bytes()))`. This reuses `write_manifest` with bytes and `target/` must be created first.
  - Fixture `example_project(tmp_path)`.
- **`tests/browser/conftest.py`**
  - The body of the `build_page` fixture becomes a plain function `page_of(project: Path, *args: str) -> tuple[Path, dict]`. It runs `cli.main` with `NO_PARSE_NO_OPEN` and returns the page and its `page_data`. `build_page` writes the config and then calls it.
  - New fixture `example_page(tmp_path, open_page) -> tuple[Page, dict]`, built with `write_example` and `page_of`.
  - This is one implementation of "build a page in a browser test" (invariant 2).

### 6. Expected values (`expected.json`)

These were computed from the generator's tables, then checked against the CLI summary of the first run (2026-11-04). Every count matched except lineage (§ below), whose difference is explained.

- **Universe:** 95 tables (18 sources, 18 staging, 38 vault, 16 marts, 3 seeds, 2 snapshots).
  - 7 domains: `sales`, `customer`, `product`, `marketing`, `finance` and `logistics` (dbt group, with owners such as `Sales Analytics`), plus `shared` (rule, `calendar`).
  - 58 relations and 110 lineage links (measured on the first run; the estimate was 106). The 106 `ref` / `source` calls give 106 links. dbt adds the 4 foreign key targets that the SQL does not reference to `depends_on`: `fct_orders` to `dim_customer`, `dim_store` and `dim_date`, and `fct_order_lines` to `dim_product`.
- **Detail:** 54 tables (13 Hub, 12 Link, 13 Satellite, 8 Fact, 8 Dimension), 58 relations.
- **Relations by origin:** 53 `relationships_test` and 5 `foreign_key` (`fct_orders` 3, `fct_order_lines` 2).
- **Untyped columns in the detail payload:** 16 (13 `hd_*`, all keys, plus 3 mart columns).
- **Detail groups (`group_by: schema`):** 2, the raw vault schema (38) and the marts schema (16). dbt-duckdb names them `main_raw_vault` and `main_marts`.

### 7. Decision D-033 (append to `docs/decisions.md`)

> **D-033 — The example project `acme_retail` is the real-manifest test input; its manifest is committed compressed and checked against dbt on demand.**
> Asked by the user on 2026-11-04 (M5.1, design note `docs/architecture/2026-11-04-m5.1-example-project.md`). `examples/acme_retail/` is a fake but complete dbt project. It has sources, staging, a Data Vault, star-schema marts in dbt groups, `relationships` tests, `foreign_key` constraints, seeds, snapshots, and a mix of typed and untyped columns. It is valid for dbt-core and dbt Fusion: `group`, `access` and `meta` sit under `config:`. It is committed as plain files and edited by hand; there is no generator. Its `dbt parse` manifest is committed as `tests/fixtures/acme_retail/manifest.json.gz`: the bytes dbt wrote, gzip level 9, `mtime=0`, at most 300 kB. It is regenerated by `tools/example_manifest.py --dbt <dbt>`, which runs `dbtscope` itself (so `dbt parse` keeps one implementation). The default tests build both views from it with `--no-parse`, so they need no dbt. A test compares the committed manifest with a fresh `dbt parse` only when `DBTSCOPE_DBT` names a dbt with dbt-duckdb, and is skipped otherwise. It compares the parsed models, because the manifest bytes change on every run. Why: the hand-built `shop` manifest let M4.4 (untyped columns) through, and only a real manifest shows what dbt writes. Rejected:
> - the raw 1.2 MB manifest (too large for a fixture);
> - a trimmed manifest (drops the unknown fields and real shapes the test is for, and ties the fixture to `manifest_schema`);
> - generating the manifest in every run (needs dbt and an adapter everywhere);
> - a `dbt` pytest marker (the documented `-m "not live and not browser"` overrides `addopts`, so it would run whenever dbt is on `PATH`);
> - committing the generator (a second source of the same files, with a drift test).

## Rejected options

- **Generator committed under `tools/` with a drift test.** Two places to change one project, plus a test that only checks the copy. Hand edits are simpler for a dbt project.
- **Committing the raw manifest (1.2 MB) or a minified one (~0.9 MB).** Both are well over the 300 kB fixture threshold, and every regeneration adds a large diff.
- **A trimmed manifest (only the fields dbtscope reads).** Not a real manifest any more (§ 2).
- **A `dbt` marker excluded by `addopts`.** The explicit `-m` of the documented commands would run it (§ 4).
- **Replacing `shop` with `acme_retail` in the unit tests and reference pages.** `shop` stays the small hand-readable fixture for unit tests and for the byte-identical M3 reference pages, which this milestone must not touch. `acme_retail` adds end-to-end coverage only.
- **A zip of the example for users** (what the user downloaded on macOS). It lives in the repository now, so a clone is enough and there is no Finder unzip caveat.

## Test plan

**Default run, `tests/integration/test_example_project.py`.** No dbt and no network.

1. `test_example_builds_both_views_without_warning`: `write_example`, then `main([--project-dir, …, --no-parse, --no-open])` returns 0.
   - stderr holds no `warning` and no `error`.
   - The summary lines match `expected.json`: universe tables / domains / relations / lineage links; detail tables with each kind count / relations; `config: …/dbt-erd.yml, preset data_vault`.
2. `test_example_domains_come_from_groups_meta_and_rules`, from the page payload:
   - a mart's domain is its dbt group, with its owner;
   - a hub's or satellite's domain is its `meta.domain`;
   - staging, sources and seeds are placed by the `domains` rules;
   - `calendar` is in `shared`;
   - there are exactly 7 domain keys.
3. `test_example_relations_come_from_tests_and_foreign_keys` (`read_manifest` only, the cheapest level):
   - the counts by origin match `expected.json`;
   - `fct_orders.customer_key → dim_customer.customer_key` is a `foreign_key`;
   - `customer_sat.hk_customer → customer_hub.hk_customer` is a `relationships_test`.
4. `test_example_mixes_typed_and_untyped_columns`: the detail payload holds 16 columns with an empty type. At least one of them is a key (`hd_*`), and typed columns are present too. This guards the fixture's M4.4 coverage.
5. `test_committed_manifest_matches_the_example`: runs only with `DBTSCOPE_DBT` (§ 4).

**Browser, `tests/browser/test_example_project.py`** (marker `browser`, served vendored libraries, no network, D-022). `test_example_page_draws_both_views`:
- The universe starts with no page error.
- Open Detail with `show_detail`. For **each** option of `#d-group` and **each** column mode of `#d-cols` (keys, all):
  - the diagram holds `svg g.node`;
  - `#d-graph` holds no `Render error`;
  - the export buttons become enabled (`wait_exportable`).
- `open_page` already fails the test on any console error.
- On this real manifest, this test catches what M4.4 missed.
