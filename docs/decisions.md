# Decisions

Each entry: the decision, why, and what it rules out. Do not reverse a decision silently: add a new entry that supersedes it (skill `/add-decision`).

## Tooling

**D-001 — Python ≥ 3.12, managed with uv; `uv.lock` is versioned.**
One tool for the interpreter, the virtual environment, dependencies and the lock file. CI runs `uv sync --locked`, so a dependency change without a lock update fails. Rejected: pip + requirements files (no lock of transitive versions), Poetry (slower, second tool).

**D-002 — Lint and format with ruff; duplicate code detected with pylint `duplicate-code`.** (CI part superseded by D-020.)
Ruff runs in CI, in pre-commit and after every Claude Code edit (`.claude/hooks/format.py`). Pylint runs only its duplicate-code checker, in pre-commit (in CI until D-020): it is the mechanical half of the one-responsibility rule (D-006); the reviewer agent covers the other half.

## Code structure

**D-003 — Source layout `src/<package>/`, pure `domain/` layer at the centre.**
`domain/` holds business rules and imports nothing else from the project; it reads no file, network, clock or environment (callers pass them in). Outer layers depend on it, never the reverse. Enforced by `tests/unit/test_layering.py`. Why: business rules stay testable in isolation and do not change when storage or interfaces change.

**D-004 — The CLI is a technical tool: English messages, explicit exit codes.** (Refined by D-029.)
0 success, 1 error, 2 usage. Errors print `<prog>: error: <message>` on stderr. Tests call `main([...])` in-process.

**D-005 — Atomic file writes only.**
Every user or state file is written by `storage/files.atomic_write` (temp file in the same folder, fsync, rename, folder fsync). A crash leaves the old file or the new one, never a mix.

**D-006 — One responsibility, one implementation.**
Each responsibility has exactly one implementation, listed in the responsibility map of `docs/architecture.md`. Duplication with a different implementation is a blocking review finding. Similar-looking code with a different responsibility is allowed.

## Working with Claude Code

**D-007 — Every change goes through `/feature`: architect → (ui-designer) → developer → tester → reviewer → documentation.**
Each agent has one job, limited tools and a ten-line report; details go into `docs/`. The architect writes a design note in `docs/architecture/` before any code. Why: decisions and designs survive the conversation, and the review checks the change against written rules rather than memory.

**D-008 — Autonomous build from the roadmap, state in `docs/progress.md`.**
`/build-roadmap` runs the milestones of `docs/roadmap.md` in order and stops on documented conditions (repeated failures, a decision to supersede, anything only the user can provide), writing `BLOCKED` and the question in `docs/progress.md`.

**D-009 — Claude Code never reads secrets and never commits or pushes on `main`.**
Enforced by `permissions.deny` in `.claude/settings.json` and by the PreToolUse hook `.claude/hooks/guard_paths.py` (secret files, protected folders, `git commit` and `git push` on `main`). Force-push, hard reset and branch deletion are denied. The user merges into `main` through pull requests.

**D-010 — Conventional Commits with a `Milestone:` footer, checked by a commit-msg hook.**
`tools/check_commit_message.py` (installed by `uv run pre-commit install`) rejects malformed messages. The footer ties every commit to a roadmap item. Git's own merge, revert and fixup messages pass unchecked.

**D-011 — English for code and repository text; the user language for what the end user sees.** (Page strings: "from locale files" superseded by D-016.)
Code, identifiers, docs, prompts, agents, skills and commits in English. UI strings and exported content in the user language, from locale files.

**D-049 — Each agent has a fixed model, set in its front matter.** (From template D-013.)
Design and review, where a mistake is costly and the work is reasoning over the whole codebase, run on the strongest model: `architect` and `reviewer` on `opus`. Implementation, tests, UI design and documentation follow a written design note or diff and run on `sonnet`. The orchestrating session keeps the user's model. Aliases follow the latest model of each family. Why: `/build-roadmap` chains dozens of agent runs; most of them do not need the strongest model. Rejected: every agent inheriting the session model (cost), `haiku` for documentation (keeping CLAUDE.md files and decisions exact needs more care than it saves).

**D-050 — `.claude/template.json` describes the link with the template; markers are enforced.** (From template D-014.)
It holds the template URL, `is_template` (false here), `synced_commit` (the template commit last brought in; this project was created from template `ee9d191`, before the file existed, and first synced to `657d64c`) and two path lists: `owned` (the template's: its changes are taken by `/sync-template` with a three-way merge) and `shared` (template and project text mixed: reviewed change by change). Every other path belongs to the project and is never synced. `tests/unit/test_template_markers.py` fails while a `TODO(project):` marker is left. The protected paths live in `.claude/guard.json`, so the guard hook itself stays template-owned. Template-owned files keep the template's wording; their references to template decisions are renumbered to this file's numbers at each sync. Rejected: copier (a second tool to install and run), a `git merge` of the template history (unrelated histories, every project edit becomes a conflict).

**D-051 — Hook commands skip uv's environment sync.** (From template D-015.)
`uv run python` checks the project environment on every call: about 0.5 s added to each tool call Claude Code makes. The guard hook runs with `uv run --no-project` (standard library only, so it also works before `uv sync`) and the format hook with `uv run --no-sync` (it needs ruff from the project environment): about 60 ms each. Rejected: `python3` (missing on Windows), the `.venv` path (differs between Windows and POSIX).

**D-052 — Package module tables and the responsibility map are checked against the code.** (From template D-016.)
`tools/doc_consistency.py`, run by `tests/unit/test_docs_consistency.py`, fails when a package module is missing from its `CLAUDE.md` table (or listed but absent), or when the responsibility map names an implementation that does not exist. A map reference names repository files by path or path suffix, any language (`domain/model`, `render/assets/common.js`, a module by its short name); a symbol must be defined in those Python files or appear as a word in the others, and a bare name must appear in the cell's files or in the package (rules in the tool's docstring; template sync `acbf7f4`). Agents rely on these tables to find existing code before writing new code (D-006); a stale table leads to duplicates. The judgement checks are the `/audit` skill's. It complements `tests/unit/test_docs.py`, which checks the user documents.

**D-053 — The CI runs locally; GitHub Actions only by hand, and only `ruff check` and the default tests.** (From template D-017.)
User decision of 2026-11-09 (template rule applied to dbtscope at the user's request). GitHub Actions minutes are not free, so during development no workflow runs on push or pull request: `.github/workflows/ci.yml` has the single trigger `workflow_dispatch`. The CI is defined once, in `tools/ci.py` (`ruff check`, then `pytest -m "not live and not browser"`); the pre-push hook and the agents run it locally, and the manual workflow runs the same script after `uv sync --locked`, on Ubuntu with Python 3.12. Any other trigger, job, step, OS or action needs an explicit request from the user and a decision that supersedes this one; `tests/unit/test_ci.py` fails otherwise. Supersedes D-043 and the CI parts of D-044: no more Windows and macOS jobs, `ruff format --check` or pinned ruff in CI; formatting, duplicate code and secrets stay checked by pre-commit, and the OS-sensitive tests run in the local suite. Rejected: keeping CI on pull requests only (still billed during development).

## Project

**D-012 — Everything comes from the dbt manifest; no warehouse connection.**
`dbtscope` runs `dbt parse` (no connection needed) and reads `target/manifest.json`. Relations between tables are the `relationships` tests (and `relationships_where`) and the `foreign_key` constraints of model contracts; lineage is `depends_on`. Why: dbt warehouses rarely declare foreign keys, and the manifest is the one place where the project's own declarations live. Rejected: reading the warehouse catalog (needs credentials, has no relations).

**D-013 — The tool is imported as `dbtscope`; the project files keep their `dbt-erd` names.**
The `dbt-erd-html` v0.2 tool became the `dbtscope` package (CLI `dbtscope`, version continued at 0.2.0). The files it reads or writes in a dbt project keep their names and format: `dbt-erd.yml`, `dbt-erd-layout.json` (format `dbt-erd-layout`, version 1), the localStorage key `dbt-erd-layout:<title>`, the default output `erd_output/erd.html`. Why: existing configs and exported arrangements keep working. Renaming them needs a superseding decision and a migration (read the old names too).

**D-014 — One self-contained HTML page that lays itself out in the browser.** (Opt-in offline page: D-021; JSON escaping: D-023; library list superseded by D-045; placement inside a domain refined by D-040.)
Python computes the data of both views and embeds it as JSON; the page computes the layout (d3-force + canvas for the universe, validated on ~1,500 nodes; Graphviz via Viz.js for the detail) and recomputes it on each filter change. The page holds structure only (names, types, descriptions), never data rows. It loads d3, Viz.js and svg-pan-zoom from public CDNs, so it needs internet access to render. Why: one file to share, no server, instant filters. Rejected: a pre-computed layout in Python (no live filters), a server app.

**D-015 — Classification by selectors and ordered rules, first match wins.** (Presets refined by D-030; refined by D-041 and D-048.)
What is drawn (`select`, `exclude`), its kind, domain and layer are lists of dbt-like selectors (`domain/selectors.py`). A table's domain is, in order: its dbt `group`, `meta.domain`, the first `domains` rule, then `group_by`. Presets (`data_vault`, `star_schema`) are plain config files. Why: any naming convention is a few lines of YAML, and dbt groups give domains with no config at all.

**D-016 — Page languages: English and French; CLI messages in English.** (Refined by D-039.)
`language: en | fr` in the config picks the page language; UI strings live in tables at the top of each page script, and labels built in Python (`Other`, `No domain`) exist in both. The CLI stays in English (D-004). Supersedes, for the page only, the "from locale files" part of D-011: the page is a single file, so its strings are inline.

**D-017 — Python ≥ 3.12 (the original tool required ≥ 3.10), PyYAML the only runtime dependency.** (Dependency clause superseded by D-025.)
Aligned with D-001. Why: one interpreter floor for the whole repository.

**D-018 — Trajectory mode (M1): lineage only, whole chain by default, dim the rest, filters never cut the chain.** (Refined by D-036.)
Settled with the user on 2026-11-03. The trajectory of a table follows `ref` / `source` lineage only, not business relations (up / down has no meaning for them). It covers the whole upstream and downstream chain by default, with a depth (1, 2, 3, all) and a direction (up, down, both) to narrow it. The universe keeps its layout: the trajectory is highlighted and the rest dimmed, so tables stay where users know them. Tables of the chain hidden by a domain, layer or type filter are brought back, as search does, and counted. Rejected: following the **Links** selector, a fixed 1–3 depth as in the Detail focus, showing the trajectory alone with a new layout, respecting the filters (the chain would look broken).

**D-019 — Browser tests carry the `browser` marker and are excluded by default; CI does not run them.** (Network part superseded by D-022.)
The page logic (universe trajectory mode first) is tested in headless Chromium with Python Playwright, under `tests/browser/`. These tests need the CDN scripts of D-014 (fetched once into the pytest cache) and a local Chromium. So, like `live` tests (invariant 5), they are excluded by `addopts` (`-m 'not live and not browser'`) and run explicitly with `uv run --group browser pytest -m browser`. Playwright sits in a separate dependency group, `browser`, which `uv sync` does not install. `playwright install` is never run by the tooling: the browser comes from `PLAYWRIGHT_BROWSERS_PATH`, or from `DBTSCOPE_CHROMIUM` (an executable path). CI does not run them: they need network access to the CDNs, a ~150 MB browser download per OS, and their timing assertions are unreliable on shared runners. They are part of the definition of done of a page milestone, run locally by the tester. Rejected: in the default suite (network, invariant 5), Node Playwright (a second runner), a CI job (cost and flakiness for little gain until the page is offline, M2).

**D-020 — Minimal CI: one Ubuntu job with ruff, the default tests and a secret scan.** (Refined by D-031 and D-032; Ubuntu-only clause superseded by D-043; secret scan in CI superseded by D-044.)
Asked by the user on 2026-11-03. `.github/workflows/ci.yml` runs one job on Ubuntu: `uv sync --locked`, `ruff check`, `ruff format --check`, `pytest -n auto -m "not live and not browser"`, then gitleaks on the pushed history. Supersedes the CI part of D-002 (pylint `duplicate-code` now runs in pre-commit only) and the test run on Windows and macOS of the template; coverage and the `dbtscope --version` smoke step are dropped too. Why: fast, cheap feedback on what matters most. Kept: `uv sync --locked` (D-001). Accepted risk: an OS-specific bug (paths, line endings) is caught only on a developer's machine.

**D-021 — M2 scope: image export of what is on screen, and an opt-in offline page with vendored libraries.** (Library list superseded by D-045; flow export refined by D-036.)
Settled with the user on 2026-11-03. M2 holds two things. (1) **Export image**: the current view exactly as shown (zoom, filters, trajectory), PNG at 2 × the screen resolution for the universe, PNG and SVG for the detail. Rejected: exporting the whole drawing whatever the zoom (unpredictable, possibly huge images). (2) **Offline page**: `--offline` / `offline: true` embeds d3, Viz.js and svg-pan-zoom, vendored in the package at the CDN versions with their licences. The default page still loads them from the CDNs (D-014 unchanged for it). Rejected: always embedding (~2.5 MB more for every page, even small projects); downloading the libraries at generation (would need network where the offline page is meant for). Not in M2: print stylesheet, small-screen fixes, plurals (roadmap "Later"). The light theme and group owners already exist.

**D-022 — Browser tests serve the page's libraries from the vendored copies; they need no network.**
Since M2 the libraries of the page are vendored in `src/dbtscope/render/vendor/` at the exact CDN versions, with their sha256 (D-021). `tests/browser/conftest.py` serves each CDN URL of `render/page.LIBRARIES` from its vendored file through `page.route` and aborts every other request; the offline page is tested with every request blocked. Supersedes the network part of D-019 ("fetched once into the pytest cache", "they need network access to the CDNs"). The rest of D-019 holds: the `browser` marker, exclusion by `addopts`, the `browser` dependency group, no `playwright install`, not in CI (browser download per OS, timing assertions on shared runners). Rejected: keeping the CDN download (network for no gain, the bytes are identical).

**D-023 — Embedded JSON escapes every `<`.**
`render/page.render_page` writes every `<` of the JSON payload as `\u003c`, the same JSON, instead of only `</` as `<\/`. Why: a dbt description holding `<!-- <script>` puts the HTML parser in the script double-escaped state, where the data block's own `</script>` no longer closes it and the page scripts after it never run. With no `<` left in the block, no data can end or disturb it. Supersedes the `</`-only rule of CLAUDE.md invariant 10 and `render/CLAUDE.md` (D-014 itself sets no escaping rule and is unchanged). The default page changes bytes only where the data holds `<`. Rejected: escaping `<!--` and `<script` one by one (easy to miss a variant such as `<SCRIPT` or `<!--` split by escapes).

**D-024 — A typed data model with pydantic v2, at four layers; the page JSON is unchanged.** (Example message refined by D-029.)
Settled with the user on 2026-11-04. Tables, columns, relations, lineage, groups, the project, the configuration and the page payloads become pydantic v2 models in `domain/` instead of `dict[str, Any]`; the manifest is read through models of the fields dbtscope uses (unknown fields ignored). Why: the data model becomes explicit and checked, key typos and malformed manifests fail early with a clear message, and the Python → JavaScript contract is written down. The JSON embedded in the page stays byte for byte what it is (positional arrays included), so the page scripts do not change. An unexpected manifest (a field dbtscope reads is missing or mistyped) stops the run with `dbtscope: error: manifest: …`, exit code 1. Rejected: validating the inputs only (the domain would keep untyped dicts); changing the page format to named objects (JavaScript changes and a larger page for no user benefit); skipping invalid nodes with a warning (a table could silently go missing from the map).

**D-025 — pydantic v2 is the second runtime dependency.** (Dependency list superseded by D-026.)
Recorded on 2026-11-04 as the consequence of D-024 (design note `docs/architecture/2026-11-04-m3-typed-model.md`). `pydantic>=2.7` joins PyYAML in `[project] dependencies`; `domain/` may import it (declared pure library, `domain/CLAUDE.md`). Supersedes, for this clause only, "PyYAML the only runtime dependency" of D-017 (the Python ≥ 3.12 floor of D-017 holds). Why: the typed model of D-024 needs it, and it replaces the hand-written validation. Accepted cost: pydantic-core is a compiled wheel (~2 MB per platform); an environment pinning pydantic v1 next to an old dbt needs an isolated install (`uv tool install`, `pipx`). Rejected: vendoring a validation library; keeping hand-written checks.

**D-026 — The CLI is built with Typer; `typer` is the third runtime dependency.**
Recorded on 2026-11-04 (M4.2, design note `docs/architecture/2026-11-04-m4.2-cli-typer.md`). `cli.py` declares its options with Typer: grouped help panels (project, dbt, output, page), a short description, examples in the epilog, `--preset` and `--view` as choices. `typer>=0.27.2` joins pydantic and PyYAML in `[project] dependencies` and brings `rich`, `shellingham` and `annotated-doc` (and rich's own dependencies); Typer 0.27 ships its own copy of click (`typer._click`), so click is not a separate dependency. The floor is the first version verified with dbtscope: 0.27.0 and 0.27.1 lack `typer.TyperException` (0.27.0 also joins the lines of the epilog), and older Typer with a separate click 8.5 crashes on `--help`. Supersedes, for this clause only, the runtime dependency list of D-025 (pydantic and PyYAML; the rest of D-025 holds). Only `cli.py` imports `typer` (and only its public names: usage errors are caught as `typer.TyperException`). The option names, `-h`, `--version`, `main(argv) -> int` and the exit codes of D-004 are kept; Typer runs with `standalone_mode=False`, so its rich error panels and pretty tracebacks are never shown and every error goes through `cli.main` (D-029). No shell-completion options (`add_completion=False`). Why: a readable, grouped `--help` and choices checked by the parser. Accepted cost: about 1 MB of pure-Python dependencies and a slower start. Rejected: argparse with a hand-made help formatter (grouping and examples by hand), `typer-slim` without rich (no help panels), Typer in standalone mode (multi-line boxed errors).

**D-027 — One word per concept (glossary in `docs/architecture.md`).**
Recorded on 2026-11-04 (M4.1, design note `docs/architecture/2026-11-04-m4.1-code-review.md` § 5). Code, tests and docs use the words of the glossary in `docs/architecture.md` (table, relation, lineage, link, kind, resource type, domain, layer, group, payload, config, licence, layout). Names protected by invariant 9 and the CLI options keep their spelling even where the glossary prefers another word (`nodes`, `entities`, `links`, the "Types" label of the page). Why: one concept, one word, so search and review work. Rejected: renaming protected keys (needs a decision superseding D-013 and a migration).

**D-028 — One practice per concern.** (Pydantic policies refined by D-030.)
Recorded on 2026-11-04 (M4.1, same design note § 4). `from __future__ import annotations` starts every Python file (ruff `I002` through `required-imports`); two pydantic policies, each one constant: `model.DOMAIN` (closed and frozen) for what dbtscope builds (domain models, payloads, `BuiltinKind`), `extra="ignore"` for what users and dbt write (`config.SETTINGS`, `manifest_schema.INPUT`); in tests, fixtures only when pytest machinery is needed (`tmp_path`, teardown, a browser), plain functions in `conftest.py` for builders and file writers; tests named `test_<behaviour>` as a fact; the page assets (`render/assets/*`) change only in a milestone that changes the page, since they are inlined and any edit changes the page bytes. Why: one way to do each thing, checked mechanically where possible.

**D-029 — CLI output: the result on stdout, the run on stderr, one line per failure.**
Recorded on 2026-11-04 (M4.2, same design note § 2–5). stdout holds only the success summary, whose first line is the absolute path of the page. stderr holds progress lines, dbt's own output (dbt runs with its stdout on our stderr, `DBT_USE_COLORS=false` when stderr is not a terminal and the variable is unset), warnings and errors. Every failure ends as one plain line `dbtscope: error: <what happened>; <what to do>` (lower case after `error:`, no final period, files named `<kind> <absolute path>`: `manifest`, `config`, `layout`, `preset`, `output`), never a traceback; a problem that does not stop the run is one `dbtscope: warning: …` line with exit code 0 (browser not opened, one view empty). Exit codes: 0 success, 1 error, 2 usage (including an unknown `--preset` and an empty path option), 130 interrupted (Ctrl-C); a closed stdout ends silently with 1. An `OSError` nobody expected is `<reason> (<path>); check the installation`; any other exception is `internal error (<type>: <message>); please report it with the command you ran`. Refines D-004 (same line format and codes, plus 130 and the form of the message) and the example message of D-024 (`manifest <path>: …` instead of `manifest: …`). Why: an error is printed next to dbt's reason, scripts read a clean result with `2>/dev/null`, CI logs stay greppable. Rejected: everything on stdout (as before: dbt's reason and our error on different streams), everything on stderr (no result channel), a `--quiet` / `--verbose` option, replaying dbt's output only on failure. User decisions of 2026-11-04: every exit-code change of the design note § 8 is approved (an unknown or empty `--preset` and every empty path option, `--project-dir ""` included, exit 2; a layout path that is a folder, a layout `version` other than 1 or a non-mapping `universe` / `detail` section, and an output that exists and is not a regular file, exit 1); errors and warnings stay plain text on stderr, with no rich colouring on a terminal (D-004 unchanged).

**D-030 — A preset can be a YAML file; every preset is validated strictly on its own.**
Settled with the user on 2026-11-04 (M4.2b, design note `docs/architecture/2026-11-04-m4.2b-preset-file.md`). A preset is a built-in name (`--preset`, choices unchanged, D-026 / D-029) or a YAML file, given by the new option `--preset-file <path>` (relative to the current folder) or by the `preset:` key of `dbt-erd.yml`. In that key, a value holding `/` or `\` or ending with `.yml` / `.yaml` is a path, read from the config file's folder with every `\` read as `/` (a `dbt-erd.yml` is shared across systems); any other value is a built-in name, and any false value (`null`, `""`, `false`, `0`, `[]`, `{}`) is no preset, as before (invariant 9). `--preset` together with `--preset-file`, or an empty `--preset-file`, is a usage error (exit 2). Precedence holds: defaults < preset < config file < command line, and a command-line preset replaces the key. Before the merge, every preset (built-in or file) is validated on its own by `domain/config.Preset`, a subclass of `Config` (rules `PresetRule`, universe `PresetUniverse`) with `PRESET_SETTINGS = ConfigDict(extra="forbid", frozen=True)`. A preset may hold every config key except `preset` (no chaining), `output` and `layout_file` (project paths). An unknown key, a refused key or a wrong type is one line `preset <abs path or name>: <key>: <problem>; fix the file`, exit 1; an unknown key is shown before the other problems. Types are those of `Config`; the only conversions accepted are the config's two shorthands (one string for a list, a number for `title` / `label`). The validated dict is merged unchanged, so built-in presets give the same pages. The run summary names the applied preset, built-in or file (`, preset <name or abs path>`). `dbt-erd.yml` stays lenient (unknown keys ignored, invariant 9) and its format is only extended: every value now read as a path was an `unknown preset` error before, so D-013 is not superseded. Refines D-015 (presets are plain config files: now a closed subset of the config keys, built in or external) and D-028 (a third model policy, `PRESET_SETTINGS`, for presets only; `DOMAIN` and `SETTINGS` unchanged). Why: teams share their own conventions without forking the package, and a misspelt key in a preset fails loudly instead of being ignored. Rejected: pydantic `strict=True` (refuses YAML lists and nested mappings, so it would need a parallel schema); a strict `dbt-erd.yml` (breaks existing files); a path in `--preset` (changes an option's meaning and D-029's exit code); chained presets; preset paths relative to the project folder.

**D-031 — CI runs on pull requests and on pushes to `main` only, with read-only permissions.** (Triggers superseded by D-032.)
Asked by the user on 2026-11-04 ("make the CI as thin as possible"). `.github/workflows/ci.yml` keeps the content of D-020 (one Ubuntu job, Python 3.12 as the floor of `requires-python`, `uv sync --locked`, ruff check and format, the default tests, gitleaks) but no longer runs on every branch push nor on manual dispatch: a branch is checked when its pull request opens or changes, and `main` after each merge. The workflow token is read-only (`contents: read`, `pull-requests: read` for gitleaks). Refines D-020. Why: a push to a branch with an open pull request ran the same job twice; nothing else needs write access. Accepted risk: a branch pushed without a pull request is checked only by the local pre-commit hooks (ruff, duplicate code, gitleaks). Rejected: dropping gitleaks or ruff from CI (pre-commit is not guaranteed to be installed), a matrix of OS or Python versions (D-020).

**D-032 — CI is paused during development: it runs only by hand, optionally on Windows and macOS.** (Superseded by D-043.)
User decision of 2026-11-04: while several pushes an hour go to the branches, the repository is private and every run counts against the Actions quota (Windows ×2, macOS ×10), so `.github/workflows/ci.yml` has no automatic trigger. It runs from Actions > ci > Run workflow; the `all-os` input adds Windows and macOS to the tests (ruff and gitleaks stay on Ubuntu). The checks are those of D-020, with a read-only token (D-031). Supersedes the triggers of D-031. Meanwhile the checks run locally and in Claude Code sessions (definition of done, `CLAUDE.md`), on Linux only. To turn CI back on: add `pull_request` and `push: branches: [main]` (D-031), keep the Windows / macOS tests manual or on `main`, and record it. Accepted risk: nothing checks a pull request automatically, and an OS-specific bug shows only when the `all-os` run is started by hand. Rejected: keeping D-031's triggers (one run per push to an open pull request), deleting the workflow (the file and the manual run stay ready).

**D-033 — The example project `acme_retail` is the real-manifest test input; its manifest is committed compressed and checked against dbt on demand.** (The example's content, marts in dbt groups and `group` / `access` / `meta` under `config:`, superseded by D-047.)
Asked by the user on 2026-11-04 (M5.1, design note `docs/architecture/2026-11-04-m5.1-example-project.md`). `examples/acme_retail/` is a fake but complete dbt project. It has sources, staging, a Data Vault, star-schema marts in dbt groups, `relationships` tests, `foreign_key` constraints, seeds, snapshots, and a mix of typed and untyped columns. It is valid for dbt-core and dbt Fusion: `group`, `access` and `meta` sit under `config:`. It is committed as plain files and edited by hand; there is no generator. **D-040 — Inside a domain, tables are placed in layer bands in the smallest circle, with no simulation.** (Refined by D-048.)
Asked by the user on 2026-11-05 (M5.5, design note `docs/architecture/2026-11-05-m5.5-universe-layout.md`).
- **Bands.** A domain's tables are placed in layer bands, left to right in the order of `DATA.layers`.
  - Inside a band, tables are ordered by in-layer lineage depth (`flowRanks`, moved to `common.js`), then by the barycentre of their neighbours in earlier bands, then by name and `unique_id`.
  - A table of the catch-all layer `other` has no layer: `flowRanks` ranks it after its parents, and it goes to the band whose rank range holds its rank (the last band when its rank is beyond every range).
- **Packing.** Each band is one column, split into balanced columns when taller than a height H; the bands are laid out in one row, and H is scanned (then the edge bands cut to the circle's chord) to give the smallest enclosing circle of the boxes' corners (`d3.packEnclose`, deterministic: fixed-seed shuffle). The radius is that circle plus 16 px at names level, 24 px at the card levels.
  - Each table reserves the room of what it shows. At names level that is the star and its label below, on two lines when the name is longer than 14 characters (split after `__`, else after the `_` nearest the middle); label widths are estimated, never measured, so the shape does not depend on fonts.
  - So reserved boxes never overlap. A circle cannot be narrower than its bands side by side: a domain with a few wide bands of few tables is flat, and its circle stays partly empty.
- **Names at a distance.** Names are drawn at 11 px whatever the zoom. At overview fewer names are drawn than before M5.5: an ordinary name that would cover another star or leave its domain's circle is hidden, and zooming in shows it. Trajectory and hovered names always compete.
- **Markers.** Faint separators between bands are drawn at constellation zoom, and the domain tooltip lists its layers.
- **De-overlap and reproducibility.** The rectangular de-overlap pass runs only around dragged tables, which never move. The placement is deterministic. The domains are still placed by d3-force with seed 42.
- **Saved arrangements are unchanged** (D-013): domain pins stay absolute, and a dragged table keeps its offset from its domain's centre, now the circle centre. Old files load, and dragged positions win. The payload is unchanged.
- **Acceptance** (revised after the first review). Every domain of 10 tables or more reaches a fill Σ w·h / π r² of at least 0.25 at names level and 0.30 at keys and all on acme_retail (0.35 on the 1,500-table payload), **or** has a radius within 15 % of the lower bound `max(W / 2, √(Σ w·h / π)) + margin`, where `W` is the bands side by side (each band's widest box plus the gaps). Measured at names / keys / all:
  - acme_retail at names: Marketing 0.351, Logistics 0.355, Sales 0.295, Finance 0.295 pass by fill; Product (0.237) passes only by the 15 % rule (1.01 of its bound).
  - acme_retail at keys and all: no domain reaches 0.30, so all pass only by the 15 % rule. At keys every domain is at 1.00 to 1.03 of its bound (Marketing 0.200, Logistics 0.244, Sales 0.215, Finance 0.189, Product 0.134); at all, Marketing (0.251), Logistics (0.291), Sales (0.257) and Finance (0.222) are at 1.05 to 1.09, Product (0.170) at about 1.0.
  - The 1,500-table payload passes by fill: 0.278 / 0.361 / 0.358.
  - Compared with before M5.5 (world radius), every acme domain is smaller at names level; at keys, Product (261 → 294), Finance (290 → 303), Customer (270 → 276) and Marketing (359 → 361) grow slightly, and Product at all (311 → 317): the old layout let their cards overlap.

Refines D-014 (d3-force now places the domains only) and the "local simulation" option of brief § 7. Rejected:
- stronger layer forces (order and overlaps depend on tuning);
- lineage-first bands as in the flow (a backward edge breaks the layer order);
- one strip per lineage depth (long chains give empty discs);

A machine without a dbt setup maps an earlier manifest (the fallback of D-054, or `--manifest`); readers who do not develop the project open the shared `erd.html`. Why: the spike showed that a placeholder profile only works with the project's real adapter. On the user's Snowflake Data Vault project, datavault4dbt has only warehouse-specific implementations of its dispatched macros, so a duckdb placeholder fails at parse time, while a snowflake placeholder parses all 1,223 models; parsing without the machine's setup would therefore make dbtscope know, choose and fetch dbt adapters. Rejected: a placeholder profile for the real adapter (B1, ties dbtscope to adapters and their required fields), a bundled dbt-core + dbt-duckdb (B2, fails on such packages and drops models enabled by `target.type`), running `dbt deps`.

**D-057 — dbt parse runs with `--log-level error` by default; `--log-level` changes it.**
Asked by the user on 2026-11-12 (M7.4, design note `docs/architecture/2026-11-12-m7.4-dbt-log-level.md`), after dozens of harmless dbt warnings buried the summary on a real project. dbtscope runs `dbt --log-level <level> parse` (global flag before the subcommand, valid from dbt-core 1.5), `<level>` from the new dbt-panel option `--log-level` (`debug`, `info`, `warn`, `error`, `none`, dbt's values), default `error`: dbt's errors are still shown, its warnings and info lines are not. The flag is always passed, so it overrides `DBT_LOG_LEVEL`. It sets the console only: dbt's `logs/dbt.log` is unchanged. `--log-level` with `--no-parse` or `--manifest` is a usage error (exit 2), like `--strict-parse`. At `none` the failure reason says `--log-level none hid dbt's messages` instead of `see above`. Refines D-029 (dbt's output on stderr, now filtered by dbt itself), D-026 (one more dbt-panel option) and D-054 (unchanged fallback, reason wording at `none`). D-012 holds: `dbt parse` is still the only dbt command. Rejected: the flag after the subcommand, the `DBT_LOG_LEVEL` env var, `--quiet`, filtering dbt's output, honouring `DBT_LOG_LEVEL`.

**D-058 — A star's size and its name's priority follow its kind's role, then its degree.**
Recorded on 2026-11-12 (M8.1, brief `docs/briefs/2026-11-12-m8-synthesis.md` § 4–5, design note `docs/architecture/2026-11-12-m8.1-roles-presets.md` § 4).
- **Tiers.** Each role (D-059) has a tier: `core` is large; `connector` and none are medium; `descriptive` and `technical` are small.
- **Size.** A star's radius is `min(cap, base + slope × √degree)`, where the degree counts every relation and lineage link of the table, as since v0.2. Large: 6 + 1.6√d, at most 16 px. Medium: 3 + 1.6√d, at most 14 px (the rule before M8.1). Small: 2 + 0.8√d, at most 6 px. The ui-designer may retune the numbers in the design note's UI design section before implementation, keeping the shape; the final values are in `docs/ui-spec.md`.
- **Names.** Names compete by tier first (large, medium, small), then by the score used before M8.1. Trajectory and hovered names keep their precedence.
- **From afar.** Below scale 0.6, when the drawn tables include a core table, the only ordinary names offered are the `FIT_NAMES` core tables with the most relations in each constellation (proposal 3).
- **Pages without roles.** They keep their sizes and names, except that sources, seeds and snapshots (built-in `technical`) are small and their names come after the models.

Supersedes the line "All stars have the same size" of `docs/brief-universe-view.md` § 3, which no longer described the page: since v0.2 the radius has grown with the degree (3 + 1.6√d, at most 14 px). Rejected: a fixed radius per role (loses the pivot tables that stand out today); one order for names and the Types list (technical before none would put source names before model names on every page without roles).

**D-059 — A kind has a role: `core`, `connector`, `descriptive`, `technical` or none.**
Recorded on 2026-11-12 (M8.1, same design note § 1–2, § 4).
- **Config.** A `kinds` rule takes an optional `role`: `core`, `connector`, `descriptive`, `technical` or `none`. Absent, `null` or empty means not set. Any other value is one line, `config <path>: kinds[N].role: invalid role 'x' (core, connector, descriptive, technical or none); fix the file`, exit 1 (as D-041). `role` belongs to kind rules only. On a domain or layer rule it is ignored in `dbt-erd.yml` and refused as an unknown key in a preset (D-030).
- **Override by key.** Lists still replace the preset's (D-015). A kind rule of `dbt-erd.yml` whose `key` is one of the preset's kinds, and which sets no role, takes that kind's role. Nothing else is inherited, and `role: none` removes the role.
- **Built-in kinds.** Source, seed and snapshot are `technical`; `other` has none.
- **Payload.** Each universe kind carries `role` (`"none"` when unset) as its last key. The order of the kinds in the payload is unchanged, so a page with no preset and no `role` differs only by that key. The detail payload gets roles in M8.5, where they are used.
- **The page.** Roles are read from the payload, never guessed from names. The universe Types list is ordered core, connector, descriptive, technical, none, and stably inside a role.
- **One meaning.** The trajectory's start, upstream and downstream is called its side (`sideOf`) in the scripts, so "role" has one meaning (D-027).

Refines D-015 (one more key on kind rules) and D-030 (presets may set it). Rejected: `role` on every rule type; inheriting the whole preset kind by key (changes what existing `kinds` lists mean); `null` in the payload for no role; sorting the payload's kinds by role in Python.

**D-060 — The built-in presets classify staging, dimensions, facts and views, give every kind a role, and set default layers by folder pattern.**
Recorded on 2026-11-12 (M8.1, same design note § 3).
- **Kinds of `data_vault`.** It gains `dim` (`dim_*`, core), `fact` (`fct_*`, core), `stg` (`stg_*`, technical) and `view` (`vw_*`, role `none`). Hub and ref hub are core; link, NH link, same-as link and bridge are connectors; satellite, ref sat and PIT are descriptive.
- **Kinds of `star_schema`.** Fact and dimension are core, bridge is a connector, and it gains `stg` (technical, the same colour as in `data_vault`).
- **Colours.** New colours reach 3:1 on the page and are at least 12 CIEDE2000 from every kind colour of both presets and from the built-in kind colours. A unit test checks them. Existing colours are unchanged.
- **Default layers.** Both presets get `layers` rules that group folders by glob: Sources (`type:source`); Staging (`stg_*`, seeds, snapshots, `raw*` except `raw*vault*`, `stg*`, `staging*`, `base*`, `bronze*`); Raw vault or Intermediate (`int*`, `vault*`, `ref*`, `silver*`, and in `data_vault` its kind globs); Data products or Marts (`dim_*`, `fct_*`…, `dp*`, `mart*`, `product*`, `gold*`); Reports (`report*`, `expo*`).
- **Project rules.** A project's own `layers` replace them, and `layers: []` restores the folder default.
- **No rules, no change.** Without `layers` rules the tool behaves as before (one layer per first folder, ordered by `FLOW_PREFIXES`, whose values are unchanged).
- **One vocabulary.** `FLOW_PREFIXES` stays the one list of folder prefixes along the flow. A unit test fails when one of its non-resource-type prefixes has no folder rule in a built-in preset, or when the presets' layers do not follow its order.
- **Pages that change.** Pages of projects using a built-in preset change: new kinds, roles, and layers by rule when the project sets none. A stored layer-mode arrangement of such a page (D-048) no longer finds its old layer keys, and computes its placement.
- **`select` is unchanged.**

Refines D-015. Rejected: generating the presets' layers from `FLOW_PREFIXES` in code, or a `layers: flow` key (presets would stop being plain, copyable files; layer labels are the convention's); adding medallion ranks to `FLOW_PREFIXES` (changes pages without rules); leaving `vw_*` without a kind (it would stay "Other", against the brief's goal).

**D-061 — A selector part that starts with `!` matches when the rest does not.**
Recorded on 2026-11-12 (M8.1, same design note § 5). The rest is a whole part, field included: `!vw_*`, `!path:models/raw*vault*`, `!tag:legacy`. Combined with `,` it narrows a selector: `path:models/int_dwh/*,!vw_*,!stg_*`. Negation applies wherever selectors do (`select`, `exclude`, the universe scope, every rule's `match`) through the one implementation, `domain/selectors.py`; `group_by: tag:<glob>` is not a selector. A bare `!` is one line, `config <path>: empty negation in '!' (write the selector after '!', such as '!vw_*'); …`, exit 1, raised when the selector is evaluated (as an unknown field). In YAML a selector that starts with `!` must be quoted (`"!vw_*"`); the user guide says so. Refines D-015 (selector syntax). Why: one folder often holds several layers (stage models, the vault, views), and a list of vault suffixes breaks when a new suffix appears; the `data_vault` preset needs it to keep `raw_vault/` out of Staging. Rejected: a separate `exclude` list per rule (a new key on every rule, and a second matching path).

**D-062 — A descriptive table has at most one parent, found by its relations, then by its name, in its own domain and layer.**
Recorded on 2026-11-12 (M8.2, `docs/architecture/2026-11-12-m8.2-entities.md` § 1–3). A table's place is its pair (domain, layer); candidates are tables whose kind has role `core` or `connector`.
- **Rule** (`domain/fold.parents`, for each table whose kind has role `descriptive`). 1. By relation: the distinct candidates the table points to (`relationships` tests and `foreign_key` constraints, D-012); exactly one is the found parent. 2. By name, when step 1 finds none or several: among the candidates of step 1 when several, else every candidate of the table's place, those whose stem equals the table's stem, or is its start followed by a character that is not a letter or a digit; the longest stem wins; a tie gives no parent. 3. Otherwise no parent. A found parent in another domain or layer is no parent, and a relation outranks a name (step 2 is not tried when step 1 found one candidate elsewhere).
- **Stem** (`fold.stem`): the table's name, lower-cased, without the fixed part (before the first and after the last wildcard) of the first positive name glob of the kind rule's selector that selects it (`selectors.name_patterns`): `vehicle_order_hub` with `*_hub` gives `vehicle_order`, `sat_vehicle_status` with `sat_*` gives `vehicle_status`. Without such a glob (a `path:` selector, an exact name, a built-in kind) the stem is the whole name.
- **Payload.** `UniverseNode.parent`, the parent's `unique_id`, `""` for none, is the last key of a node.
- **CLI.** The summary gets a `folded:` row, only when a kind has role `descriptive`: `440 descriptive tables into their parent, 2 without a parent`, with `; shown when the page opens (universe.fold: false)` when the fold is off by default.
- **Not read:** lineage (a satellite is built from stage models, not from its hub). No opt-out key for the name step: a wrong fold is corrected by a `relationships` test, by the kind's role, or by `universe.fold: false`.

Refines D-059 (roles now drive a rule in Python) and D-012 (relations are used for one more purpose; still the manifest only). Rejected: folding into a parent of another domain or layer (a table would leave the constellation that counts it); breaking a tie by role, order or name (an invisible guess); lineage as a step; comparing a candidate's stem with the table's full name (fails prefix conventions such as `sat_*`); omitting `parent` when empty (D-048's reason).

**D-063 — The universe folds descriptive tables into their entity, without reducing any count.**
Recorded on 2026-11-12 (M8.2, same design note § 4 and UI design). An **entity** is a drawn `core` or `connector` table; **fold** is drawing a descriptive table inside its parent's star (the opposite is **show**).
- **Three sets.** Passing (the domain, layer and type filters), folded now (passing tables with a parent, when the fold is on, whose parent passes, whose parent is not the entity opened by a search, and that are not trajectory members), drawn (passing minus folded now). A table whose parent is filtered out is drawn as its own star.
- **Counts.** The meta line (tables, links), constellation counts, composition bars, tooltips and band counts are over passing tables, folded included; the meta line adds `N entities` while the fold is on. Table-level links of folded tables are not drawn; the routes and the flow direction between constellations count them.
- **Drawing.** An entity holding at least one table carries a badge (a dark disc with a white outline on the star's upper right, a dot at Fit, the count when zoomed in); its tooltip lists the folded tables, its card lists them under the columns (12 then "+ N"). A shown table that has a parent says "Folds into: <parent>" in its tooltip.
- **Reachability.** Search opens the entity of a folded table (one at a time); a trajectory draws its members unfolded (a relayout, as `reveal` already does for filtered-out tables); double-click is unchanged.
- **Control and config.** One checkbox in the universe panel after Constellations, shown only when a table has a parent. Config `universe.fold` (boolean, default true) gives `defaults.fold`, the last key of the universe defaults. The viewer's choice is kept in localStorage `dbtscope-fold:<title>` (`folded` / `shown`), only when it differs from the default, never in the layout, never exported.

Refines D-018 (a trajectory may relayout to show its folded members), D-048 (one more config key, payload key and viewer key, under the same rules) and D-058 (folding does not change the star's radius). Rejected: hiding the folded tables of a filtered-out entity or drawing a ghost entity; drawing a folded table's links from its entity inside the domain; unfolded trajectory members on an orbit around the entity without a relayout; Python deciding whether the control shows; the fold state in the exported layout.

**D-064 — The folded drawing keeps its own arrangement.**
Recorded on 2026-11-12 (M8.2, same design note § 4.7). The `universe` section of the layout gains the scopes `folded:names`, `folded:keys`, `folded:all`, `layers:folded:names`, `layers:folded:keys` and `layers:folded:all`, each with the shape of its unfolded twin. The folded drawing's discs are about half the area of the shown ones, so pins saved in one state would overlap or leave gaps in the other. A stored offset of a folded table lives in the unfolded scope and applies again when the table is shown. Files and stored arrangements from before M8.2 are arrangements of the shown drawing: they load into the unfolded scopes unchanged. Older pages ignore the new scopes and keep them on export; Reset layout clears every scope. The format, its version, the file name and the localStorage key `dbt-erd-layout:<title>` are unchanged.

Extends D-013's content as D-048 did, without superseding it. Rejected: one scope for both states; a new top-level section or format version; the fold state inside the exported layout.

**D-065 — At overview scale a constellation is drawn as a summary card, by one rule on the drawn size of stars.**
Recorded on 2026-11-12 (M8.3, `docs/architecture/2026-11-12-m8.3-summary-cards.md` § 2, § 3 and UI design). The reference radius is the median radius of the drawn stars of the highest tier present; with `s` = scale × that radius, the cards' weight is 0 from `s` = 3 px up, 1 from 2 px down, linear in log scale between (a ratio of 1.5, about three wheel notches); stars, links, names and halos fade by `1 − weight`, cards by the weight; the camera never moves for it and nothing is stored. The card is a rounded rectangle 1.8 r wide and high centred on the constellation, moved with it; the corner radius is 0.4 r on screen, at most max(28 px, 0.24 r), so the corners stay within 1.18 r of the centre at every zoom (the collision radius of the layout is 1.15 r + 30) and the text can be inset from them. No layout, payload, config or CLI change. The pointer acts on cards from weight 0.5. Pages open on cards when Fit is below the band (the large project: Fit 0.181, band 0.195 to 0.293) and on stars when it is above (acme_retail at 1280 × 800: Fit 0.447, band 0.209 to 0.313); a viewer who zooms out past Fit, or a narrow screen, may see cards on a small project too. Refines D-058 (names at Fit apply where stars are drawn), D-040 (no layout change; table names fade with their stars) and the zoom levels of `docs/brief-universe-view.md` § 4.

**D-066 — A summary card shows counts, rows by layer or domain with a kind bar, and the main tables; it can be read as text.**
