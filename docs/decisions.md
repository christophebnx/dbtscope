# Decisions

Each entry: the decision, why, and what it rules out. Do not reverse a decision silently: add a new entry that supersedes it (skill `/add-decision`).

## Tooling

**D-001 — Python ≥ 3.12, managed with uv; `uv.lock` is versioned.**
One tool for the interpreter, the virtual environment, dependencies and the lock file. CI runs `uv sync --locked`, so a dependency change without a lock update fails. Rejected: pip + requirements files (no lock of transitive versions), Poetry (slower, second tool).

**D-002 — Lint and format with ruff; duplicate code detected with pylint `duplicate-code`.** (CI part superseded by D-020.)
Ruff runs in CI, in pre-commit and after every Claude Code edit (`.claude/hooks/format.py`). Pylint runs only its duplicate-code checker, in pre-commit (in CI until D-020): it is the mechanical half of the one-responsibility rule (D-006); the reviewer agent covers the other half.

## Code structure

**D-003 — Source layout `src/<package>/`, pure `domain/` layer at the centre.**
`domain/` holds business rules and imports nothing else from the project; it reads no file, network, clock or environment (callers pass them in). Outer layers depend on it, never the reverse. Enforced by `tests/unit/test_layering.py`. Why: business rules stay testable in isolation and do not change when storage or interfaces change.

**D-004 — The CLI is a technical tool: English messages, explicit exit codes.** (Refined by D-029.)
0 success, 1 error, 2 usage. Errors print `<prog>: error: <message>` on stderr. Tests call `main([...])` in-process.

**D-005 — Atomic file writes only.**
Every user or state file is written by `storage/files.atomic_write` (temp file in the same folder, fsync, rename, folder fsync). A crash leaves the old file or the new one, never a mix.

**D-006 — One responsibility, one implementation.**
Each responsibility has exactly one implementation, listed in the responsibility map of `docs/architecture.md`. Duplication with a different implementation is a blocking review finding. Similar-looking code with a different responsibility is allowed.

## Working with Claude Code

**D-007 — Every change goes through `/feature`: architect → (ui-designer) → developer → tester → reviewer → documentation.**
Each agent has one job, limited tools and a ten-line report; details go into `docs/`. The architect writes a design note in `docs/architecture/` before any code. Why: decisions and designs survive the conversation, and the review checks the change against written rules rather than memory.

**D-008 — Autonomous build from the roadmap, state in `docs/progress.md`.**
`/build-roadmap` runs the milestones of `docs/roadmap.md` in order and stops on documented conditions (repeated failures, a decision to supersede, anything only the user can provide), writing `BLOCKED` and the question in `docs/progress.md`.

**D-009 — Claude Code never reads secrets and never commits or pushes on `main`.**
Enforced by `permissions.deny` in `.claude/settings.json` and by the PreToolUse hook `.claude/hooks/guard_paths.py` (secret files, protected folders, `git commit` and `git push` on `main`). Force-push, hard reset and branch deletion are denied. The user merges into `main` through pull requests.

**D-010 — Conventional Commits with a `Milestone:` footer, checked by a commit-msg hook.**
`tools/check_commit_message.py` (installed by `uv run pre-commit install`) rejects malformed messages. The footer ties every commit to a roadmap item. Git's own merge, revert and fixup messages pass unchecked.

**D-011 — English for code and repository text; the user language for what the end user sees.** (Page strings: "from locale files" superseded by D-016.)
Code, identifiers, docs, prompts, agents, skills and commits in English. UI strings and exported content in the user language, from locale files.

## Project

**D-012 — Everything comes from the dbt manifest; no warehouse connection.**
`dbtscope` runs `dbt parse` (no connection needed) and reads `target/manifest.json`. Relations between tables are the `relationships` tests (and `relationships_where`) and the `foreign_key` constraints of model contracts; lineage is `depends_on`. Why: dbt warehouses rarely declare foreign keys, and the manifest is the one place where the project's own declarations live. Rejected: reading the warehouse catalog (needs credentials, has no relations).

**D-013 — The tool is imported as `dbtscope`; the project files keep their `dbt-erd` names.**
The `dbt-erd-html` v0.2 tool became the `dbtscope` package (CLI `dbtscope`, version continued at 0.2.0). The files it reads or writes in a dbt project keep their names and format: `dbt-erd.yml`, `dbt-erd-layout.json` (format `dbt-erd-layout`, version 1), the localStorage key `dbt-erd-layout:<title>`, the default output `erd_output/erd.html`. Why: existing configs and exported arrangements keep working. Renaming them needs a superseding decision and a migration (read the old names too).

**D-014 — One self-contained HTML page that lays itself out in the browser.** (Opt-in offline page: D-021; JSON escaping: D-023.)
Python computes the data of both views and embeds it as JSON; the page computes the layout (d3-force + canvas for the universe, validated on ~1,500 nodes; Graphviz via Viz.js for the detail) and recomputes it on each filter change. The page holds structure only (names, types, descriptions), never data rows. It loads d3, Viz.js and svg-pan-zoom from public CDNs, so it needs internet access to render. Why: one file to share, no server, instant filters. Rejected: a pre-computed layout in Python (no live filters), a server app.

**D-015 — Classification by selectors and ordered rules, first match wins.** (Presets refined by D-030.)
What is drawn (`select`, `exclude`), its kind, domain and layer are lists of dbt-like selectors (`domain/selectors.py`). A table's domain is, in order: its dbt `group`, `meta.domain`, the first `domains` rule, then `group_by`. Presets (`data_vault`, `star_schema`) are plain config files. Why: any naming convention is a few lines of YAML, and dbt groups give domains with no config at all.

**D-016 — Page languages: English and French; CLI messages in English.**
`language: en | fr` in the config picks the page language; UI strings live in tables at the top of each page script, and labels built in Python (`Other`, `No domain`) exist in both. The CLI stays in English (D-004). Supersedes, for the page only, the "from locale files" part of D-011: the page is a single file, so its strings are inline.

**D-017 — Python ≥ 3.12 (the original tool required ≥ 3.10), PyYAML the only runtime dependency.** (Dependency clause superseded by D-025.)
Aligned with D-001. Why: one interpreter floor for the whole repository.

**D-018 — Trajectory mode (M1): lineage only, whole chain by default, dim the rest, filters never cut the chain.**
Settled with the user on 2026-11-03. The trajectory of a table follows `ref` / `source` lineage only, not business relations (up / down has no meaning for them). It covers the whole upstream and downstream chain by default, with a depth (1, 2, 3, all) and a direction (up, down, both) to narrow it. The universe keeps its layout: the trajectory is highlighted and the rest dimmed, so tables stay where users know them. Tables of the chain hidden by a domain, layer or type filter are brought back, as search does, and counted. Rejected: following the **Links** selector, a fixed 1–3 depth as in the Detail focus, showing the trajectory alone with a new layout, respecting the filters (the chain would look broken).

**D-019 — Browser tests carry the `browser` marker and are excluded by default; CI does not run them.** (Network part superseded by D-022.)
The page logic (universe trajectory mode first) is tested in headless Chromium with Python Playwright, under `tests/browser/`. These tests need the CDN scripts of D-014 (fetched once into the pytest cache) and a local Chromium. So, like `live` tests (invariant 5), they are excluded by `addopts` (`-m 'not live and not browser'`) and run explicitly with `uv run --group browser pytest -m browser`. Playwright sits in a separate dependency group, `browser`, which `uv sync` does not install. `playwright install` is never run by the tooling: the browser comes from `PLAYWRIGHT_BROWSERS_PATH`, or from `DBTSCOPE_CHROMIUM` (an executable path). CI does not run them: they need network access to the CDNs, a ~150 MB browser download per OS, and their timing assertions are unreliable on shared runners. They are part of the definition of done of a page milestone, run locally by the tester. Rejected: in the default suite (network, invariant 5), Node Playwright (a second runner), a CI job (cost and flakiness for little gain until the page is offline, M2).

**D-020 — Minimal CI: one Ubuntu job with ruff, the default tests and a secret scan.** (Refined by D-031 and D-032.)
Asked by the user on 2026-11-03. `.github/workflows/ci.yml` runs one job on Ubuntu: `uv sync --locked`, `ruff check`, `ruff format --check`, `pytest -n auto -m "not live and not browser"`, then gitleaks on the pushed history. Supersedes the CI part of D-002 (pylint `duplicate-code` now runs in pre-commit only) and the test run on Windows and macOS of the template; coverage and the `dbtscope --version` smoke step are dropped too. Why: fast, cheap feedback on what matters most. Kept: `uv sync --locked` (D-001). Accepted risk: an OS-specific bug (paths, line endings) is caught only on a developer's machine.

**D-021 — M2 scope: image export of what is on screen, and an opt-in offline page with vendored libraries.**
Settled with the user on 2026-11-03. M2 holds two things. (1) **Export image**: the current view exactly as shown (zoom, filters, trajectory), PNG at 2 × the screen resolution for the universe, PNG and SVG for the detail. Rejected: exporting the whole drawing whatever the zoom (unpredictable, possibly huge images). (2) **Offline page**: `--offline` / `offline: true` embeds d3, Viz.js and svg-pan-zoom, vendored in the package at the CDN versions with their licences. The default page still loads them from the CDNs (D-014 unchanged for it). Rejected: always embedding (~2.5 MB more for every page, even small projects); downloading the libraries at generation (would need network where the offline page is meant for). Not in M2: print stylesheet, small-screen fixes, plurals (roadmap "Later"). The light theme and group owners already exist.

**D-022 — Browser tests serve the page's libraries from the vendored copies; they need no network.**
Since M2 the libraries of the page are vendored in `src/dbtscope/render/vendor/` at the exact CDN versions, with their sha256 (D-021). `tests/browser/conftest.py` serves each CDN URL of `render/page.LIBRARIES` from its vendored file through `page.route` and aborts every other request; the offline page is tested with every request blocked. Supersedes the network part of D-019 ("fetched once into the pytest cache", "they need network access to the CDNs"). The rest of D-019 holds: the `browser` marker, exclusion by `addopts`, the `browser` dependency group, no `playwright install`, not in CI (browser download per OS, timing assertions on shared runners). Rejected: keeping the CDN download (network for no gain, the bytes are identical).

**D-023 — Embedded JSON escapes every `<`.**
`render/page.render_page` writes every `<` of the JSON payload as `\u003c`, the same JSON, instead of only `</` as `<\/`. Why: a dbt description holding `<!-- <script>` puts the HTML parser in the script double-escaped state, where the data block's own `</script>` no longer closes it and the page scripts after it never run. With no `<` left in the block, no data can end or disturb it. Supersedes the `</`-only rule of CLAUDE.md invariant 10 and `render/CLAUDE.md` (D-014 itself sets no escaping rule and is unchanged). The default page changes bytes only where the data holds `<`. Rejected: escaping `<!--` and `<script` one by one (easy to miss a variant such as `<SCRIPT` or `<!--` split by escapes).

**D-024 — A typed data model with pydantic v2, at four layers; the page JSON is unchanged.** (Example message refined by D-029.)
Settled with the user on 2026-11-04. Tables, columns, relations, lineage, groups, the project, the configuration and the page payloads become pydantic v2 models in `domain/` instead of `dict[str, Any]`; the manifest is read through models of the fields dbtscope uses (unknown fields ignored). Why: the data model becomes explicit and checked, key typos and malformed manifests fail early with a clear message, and the Python → JavaScript contract is written down. The JSON embedded in the page stays byte for byte what it is (positional arrays included), so the page scripts do not change. An unexpected manifest (a field dbtscope reads is missing or mistyped) stops the run with `dbtscope: error: manifest: …`, exit code 1. Rejected: validating the inputs only (the domain would keep untyped dicts); changing the page format to named objects (JavaScript changes and a larger page for no user benefit); skipping invalid nodes with a warning (a table could silently go missing from the map).

**D-025 — pydantic v2 is the second runtime dependency.** (Dependency list superseded by D-026.)
Recorded on 2026-11-04 as the consequence of D-024 (design note `docs/architecture/2026-11-04-m3-typed-model.md`). `pydantic>=2.7` joins PyYAML in `[project] dependencies`; `domain/` may import it (declared pure library, `domain/CLAUDE.md`). Supersedes, for this clause only, "PyYAML the only runtime dependency" of D-017 (the Python ≥ 3.12 floor of D-017 holds). Why: the typed model of D-024 needs it, and it replaces the hand-written validation. Accepted cost: pydantic-core is a compiled wheel (~2 MB per platform); an environment pinning pydantic v1 next to an old dbt needs an isolated install (`uv tool install`, `pipx`). Rejected: vendoring a validation library; keeping hand-written checks.

**D-026 — The CLI is built with Typer; `typer` is the third runtime dependency.**
Recorded on 2026-11-04 (M4.2, design note `docs/architecture/2026-11-04-m4.2-cli-typer.md`). `cli.py` declares its options with Typer: grouped help panels (project, dbt, output, page), a short description, examples in the epilog, `--preset` and `--view` as choices. `typer>=0.27.2` joins pydantic and PyYAML in `[project] dependencies` and brings `rich`, `shellingham` and `annotated-doc` (and rich's own dependencies); Typer 0.27 ships its own copy of click (`typer._click`), so click is not a separate dependency. The floor is the first version verified with dbtscope: 0.27.0 and 0.27.1 lack `typer.TyperException` (0.27.0 also joins the lines of the epilog), and older Typer with a separate click 8.5 crashes on `--help`. Supersedes, for this clause only, the runtime dependency list of D-025 (pydantic and PyYAML; the rest of D-025 holds). Only `cli.py` imports `typer` (and only its public names: usage errors are caught as `typer.TyperException`). The option names, `-h`, `--version`, `main(argv) -> int` and the exit codes of D-004 are kept; Typer runs with `standalone_mode=False`, so its rich error panels and pretty tracebacks are never shown and every error goes through `cli.main` (D-029). No shell-completion options (`add_completion=False`). Why: a readable, grouped `--help` and choices checked by the parser. Accepted cost: about 1 MB of pure-Python dependencies and a slower start. Rejected: argparse with a hand-made help formatter (grouping and examples by hand), `typer-slim` without rich (no help panels), Typer in standalone mode (multi-line boxed errors).

**D-027 — One word per concept (glossary in `docs/architecture.md`).**
Recorded on 2026-11-04 (M4.1, design note `docs/architecture/2026-11-04-m4.1-code-review.md` § 5). Code, tests and docs use the words of the glossary in `docs/architecture.md` (table, relation, lineage, link, kind, resource type, domain, layer, group, payload, config, licence, layout). Names protected by invariant 9 and the CLI options keep their spelling even where the glossary prefers another word (`nodes`, `entities`, `links`, the "Types" label of the page). Why: one concept, one word, so search and review work. Rejected: renaming protected keys (needs a decision superseding D-013 and a migration).

**D-028 — One practice per concern.** (Pydantic policies refined by D-030.)
Recorded on 2026-11-04 (M4.1, same design note § 4). `from __future__ import annotations` starts every Python file (ruff `I002` through `required-imports`); two pydantic policies, each one constant: `model.DOMAIN` (closed and frozen) for what dbtscope builds (domain models, payloads, `BuiltinKind`), `extra="ignore"` for what users and dbt write (`config.SETTINGS`, `manifest_schema.INPUT`); in tests, fixtures only when pytest machinery is needed (`tmp_path`, teardown, a browser), plain functions in `conftest.py` for builders and file writers; tests named `test_<behaviour>` as a fact; the page assets (`render/assets/*`) change only in a milestone that changes the page, since they are inlined and any edit changes the page bytes. Why: one way to do each thing, checked mechanically where possible.

**D-029 — CLI output: the result on stdout, the run on stderr, one line per failure.**
Recorded on 2026-11-04 (M4.2, same design note § 2–5). stdout holds only the success summary, whose first line is the absolute path of the page. stderr holds progress lines, dbt's own output (dbt runs with its stdout on our stderr, `DBT_USE_COLORS=false` when stderr is not a terminal and the variable is unset), warnings and errors. Every failure ends as one plain line `dbtscope: error: <what happened>; <what to do>` (lower case after `error:`, no final period, files named `<kind> <absolute path>`: `manifest`, `config`, `layout`, `preset`, `output`), never a traceback; a problem that does not stop the run is one `dbtscope: warning: …` line with exit code 0 (browser not opened, one view empty). Exit codes: 0 success, 1 error, 2 usage (including an unknown `--preset` and an empty path option), 130 interrupted (Ctrl-C); a closed stdout ends silently with 1. An `OSError` nobody expected is `<reason> (<path>); check the installation`; any other exception is `internal error (<type>: <message>); please report it with the command you ran`. Refines D-004 (same line format and codes, plus 130 and the form of the message) and the example message of D-024 (`manifest <path>: …` instead of `manifest: …`). Why: an error is printed next to dbt's reason, scripts read a clean result with `2>/dev/null`, CI logs stay greppable. Rejected: everything on stdout (as before: dbt's reason and our error on different streams), everything on stderr (no result channel), a `--quiet` / `--verbose` option, replaying dbt's output only on failure. User decisions of 2026-11-04: every exit-code change of the design note § 8 is approved (an unknown or empty `--preset` and every empty path option, `--project-dir ""` included, exit 2; a layout path that is a folder, a layout `version` other than 1 or a non-mapping `universe` / `detail` section, and an output that exists and is not a regular file, exit 1); errors and warnings stay plain text on stderr, with no rich colouring on a terminal (D-004 unchanged).

**D-030 — A preset can be a YAML file; every preset is validated strictly on its own.**
Settled with the user on 2026-11-04 (M4.2b, design note `docs/architecture/2026-11-04-m4.2b-preset-file.md`). A preset is a built-in name (`--preset`, choices unchanged, D-026 / D-029) or a YAML file, given by the new option `--preset-file <path>` (relative to the current folder) or by the `preset:` key of `dbt-erd.yml`. In that key, a value holding `/` or `\` or ending with `.yml` / `.yaml` is a path, read from the config file's folder with every `\` read as `/` (a `dbt-erd.yml` is shared across systems); any other value is a built-in name, and any false value (`null`, `""`, `false`, `0`, `[]`, `{}`) is no preset, as before (invariant 9). `--preset` together with `--preset-file`, or an empty `--preset-file`, is a usage error (exit 2). Precedence holds: defaults < preset < config file < command line, and a command-line preset replaces the key. Before the merge, every preset (built-in or file) is validated on its own by `domain/config.Preset`, a subclass of `Config` (rules `PresetRule`, universe `PresetUniverse`) with `PRESET_SETTINGS = ConfigDict(extra="forbid", frozen=True)`. A preset may hold every config key except `preset` (no chaining), `output` and `layout_file` (project paths). An unknown key, a refused key or a wrong type is one line `preset <abs path or name>: <key>: <problem>; fix the file`, exit 1; an unknown key is shown before the other problems. Types are those of `Config`; the only conversions accepted are the config's two shorthands (one string for a list, a number for `title` / `label`). The validated dict is merged unchanged, so built-in presets give the same pages. The run summary names the applied preset, built-in or file (`, preset <name or abs path>`). `dbt-erd.yml` stays lenient (unknown keys ignored, invariant 9) and its format is only extended: every value now read as a path was an `unknown preset` error before, so D-013 is not superseded. Refines D-015 (presets are plain config files: now a closed subset of the config keys, built in or external) and D-028 (a third model policy, `PRESET_SETTINGS`, for presets only; `DOMAIN` and `SETTINGS` unchanged). Why: teams share their own conventions without forking the package, and a misspelt key in a preset fails loudly instead of being ignored. Rejected: pydantic `strict=True` (refuses YAML lists and nested mappings, so it would need a parallel schema); a strict `dbt-erd.yml` (breaks existing files); a path in `--preset` (changes an option's meaning and D-029's exit code); chained presets; preset paths relative to the project folder.

**D-031 — CI runs on pull requests and on pushes to `main` only, with read-only permissions.** (Triggers superseded by D-032.)
Asked by the user on 2026-11-04 ("make the CI as thin as possible"). `.github/workflows/ci.yml` keeps the content of D-020 (one Ubuntu job, Python 3.12 as the floor of `requires-python`, `uv sync --locked`, ruff check and format, the default tests, gitleaks) but no longer runs on every branch push nor on manual dispatch: a branch is checked when its pull request opens or changes, and `main` after each merge. The workflow token is read-only (`contents: read`, `pull-requests: read` for gitleaks). Refines D-020. Why: a push to a branch with an open pull request ran the same job twice; nothing else needs write access. Accepted risk: a branch pushed without a pull request is checked only by the local pre-commit hooks (ruff, duplicate code, gitleaks). Rejected: dropping gitleaks or ruff from CI (pre-commit is not guaranteed to be installed), a matrix of OS or Python versions (D-020).

**D-032 — CI is paused during development: it runs only by hand, optionally on Windows and macOS.**
User decision of 2026-11-04: while several pushes an hour go to the branches, the repository is private and every run counts against the Actions quota (Windows ×2, macOS ×10), so `.github/workflows/ci.yml` has no automatic trigger. It runs from Actions > ci > Run workflow; the `all-os` input adds Windows and macOS to the tests (ruff and gitleaks stay on Ubuntu). The checks are those of D-020, with a read-only token (D-031). Supersedes the triggers of D-031. Meanwhile the checks run locally and in Claude Code sessions (definition of done, `CLAUDE.md`), on Linux only. To turn CI back on: add `pull_request` and `push: branches: [main]` (D-031), keep the Windows / macOS tests manual or on `main`, and record it. Accepted risk: nothing checks a pull request automatically, and an OS-specific bug shows only when the `all-os` run is started by hand. Rejected: keeping D-031's triggers (one run per push to an open pull request), deleting the workflow (the file and the manual run stay ready).

**D-033 — The example project `acme_retail` is the real-manifest test input; its manifest is committed compressed and checked against dbt on demand.**
Asked by the user on 2026-11-04 (M5.1, design note `docs/architecture/2026-11-04-m5.1-example-project.md`). `examples/acme_retail/` is a fake but complete dbt project. It has sources, staging, a Data Vault, star-schema marts in dbt groups, `relationships` tests, `foreign_key` constraints, seeds, snapshots, and a mix of typed and untyped columns. It is valid for dbt-core and dbt Fusion: `group`, `access` and `meta` sit under `config:`. It is committed as plain files and edited by hand; there is no generator. Its `dbt parse` manifest is committed as `tests/fixtures/acme_retail/manifest.json.gz`: the bytes dbt wrote, gzip level 9, `mtime=0`, at most 300 kB. It is regenerated by `tools/example_manifest.py --dbt <dbt>`, which runs `dbtscope` itself (so `dbt parse` keeps one implementation). The default tests build both views from it with `--no-parse`, so they need no dbt. A test compares the committed manifest with a fresh `dbt parse` only when `DBTSCOPE_DBT` names a dbt with dbt-duckdb, and is skipped otherwise. It compares the parsed models, because the manifest bytes change on every run. Why: the hand-built `shop` manifest let M4.4 (untyped columns) through, and only a real manifest shows what dbt writes. Rejected:
- the raw 1.2 MB manifest (too large for a fixture);
- a trimmed manifest (drops the unknown fields and real shapes the test is for, and ties the fixture to `manifest_schema`);
- generating the manifest in every run (needs dbt and an adapter everywhere);
- a `dbt` pytest marker (the documented `-m "not live and not browser"` overrides `addopts`, so it would run whenever dbt is on `PATH`);
- committing the generator (a second source of the same files, with a drift test).

**D-034 — dbtscope is licensed under the Apache License 2.0.**
User decision of 2026-11-04. `LICENSE` holds the Apache License 2.0 text (as published at apache.org), `NOTICE` the copyright line (Christophe B., 2026) and a pointer to the licences of the vendored libraries; `pyproject.toml` declares `license = "Apache-2.0"`. Replaces the MIT licence of the template (not recorded until now). The licences of the libraries embedded in offline pages (d3, Viz.js, svg-pan-zoom, and Graphviz, Expat, Emscripten and musl inside `full.render.js`, D-021) are unchanged and still ship with them. Why: the user's choice; Apache 2.0 adds an explicit patent grant and a NOTICE convention. The project has a single human author, so no other contributor's consent is needed.

**D-035 — On narrow screens the side panels start closed.**
User decision of 2026-11-04 (M5.2, design note `docs/architecture/2026-11-04-m5.2-page-polish.md`). When a view of the page starts (its first showing) in a window 600 px wide or narrower (the `page.css` breakpoint), its filter panel starts closed and its ☰ button says `aria-expanded="false"`. Wider windows open as before. The state is not saved and does not follow later resizing: the ☰ button decides. At 600 px or narrower an open panel stacks above the toolbar, full width, at most 45 % of the window height and scrolling inside itself, so the page never scrolls sideways. On coarse pointers (`@media (pointer: coarse)`), every control of the page is a 44 px target; fine-pointer (desktop) rendering is unchanged. Why: at 360 px the 260 px panel left about 100 px of canvas, so the map was unusable until the user found the toggle. Rejected: closing it with CSS alone (the toggle state would be wrong), remembering the state (a new stored state, D-013), 44 px targets for fine pointers too (changes the desktop page).

**D-036 — The flow view: a trajectory drawn left to right by Graphviz, in an overlay of the Universe tab.**
Asked by the user on 2026-11-04 (M5.3, design note `docs/architecture/2026-11-04-m5.3-flow-view.md`). A **Flow** button in the trajectory bar opens the current trajectory (same start, direction and depth) as a left-to-right Graphviz diagram (Viz.js, as the detail view). It shows upstream tables on the left, the start emphasised and downstream tables on the right. Each table shows its depth (`−n` / `+n`), its kind colour (as in the universe) and its domain as a colour band listed in a legend. The universe filters do not apply (D-018). Columns are computed in the page by `flowRanks`: lineage comes first, so every edge goes left to right, and the configured layer order is a floor, so layers become column bands wherever the lineage follows them. A click on a table recentres the flow. **Back** or `Esc` returns to the universe exactly as it was: the flow is an overlay over the whole Universe tab (panel and stage made `inert`), not a tab, and it saves nothing (no layout, D-013). It exports PNG and SVG, named `<title>-flow.png|svg`, through the detail view's export helpers, moved to `common.js`. This extends the file names of D-021.
