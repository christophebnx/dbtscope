# render/ — rules

- Builds the single self-contained HTML page from the view data computed in `domain/`. No business rule here: what is drawn, grouped and coloured is decided in `domain/detail.py` and `domain/universe.py`.
- Imports allowed: the standard library and `domain`. Reads its own assets through `importlib.resources`, never from the working directory.
- **No edit under `assets/` outside a milestone that changes the page** (D-028): the assets are inlined, so any edit, even a comment or whitespace, changes the page bytes checked by `tests/fixtures/m3-reference-pages/`, and may change the page sizes the user guide's summaries quote (`tests/unit/test_docs.py`): update both in the same commit.
- The page lays itself out in the browser (bands packed into discs, d3-force for the constellations and a canvas for the universe, D-040, D-048; Graphviz via Viz.js for the detail and the flow view); Python only embeds the data as JSON.
- The embedded JSON is `domain/payload.PagePayload` serialised by `embedded_json`: `model_dump(by_alias=True)` then the one `json.dumps(ensure_ascii=False, separators=(",", ":"))`, never `model_dump_json` (one encoder, byte identity with `tests/fixtures/m3-reference-pages/`).
- Every `<` in the embedded JSON is escaped as `\u003c` (D-023), so data can never close or disturb a `<script>` block. Every `</script` of an inlined library (and of its licence banner) is escaped as `<\/script`; a vendored file, script or licence, must hold none of `UNSAFE_MARKUP` (`<!--`, `<script`; checked by `tools/vendor_libraries.py` and `tests/unit/test_vendor.py`).
- The JS writes and reads the layout format `dbt-erd-layout` (`domain/layout.LAYOUT_FORMAT`, written once in boot.js as `LAYOUT_FORMAT`) and the localStorage key `dbt-erd-layout:<title>`: change them only with a decision that supersedes D-013. The `universe` section is a mapping of scopes: `names`, `keys`, `all` (domain constellations, `{domains, nodes}`) `layers:names`, `layers:keys`, `layers:all` (layer constellations, `{layers, nodes}`, D-048) and, for the drawing with the descriptive tables folded, `folded:names|keys|all` and `layers:folded:names|keys|all` (D-064); a new scope extends the content, never the format. The `detail` section is a mapping of drawing keys (`group|focus|depth|columns|types`), with a sixth part `fold` only for a skeleton (D-075) and `grid` for the shown drawing of a large group (D-078). The viewer's grouping and fold choices live apart, in the localStorage keys `dbtscope-constellations:<title>`, `dbtscope-fold:<title>`, `dbtscope-cards:<title>` (D-081), `dbtscope-routes:<title>` (D-083) and `dbtscope-detail-fold:<title>` (`universe.js byMemory`, `foldMemory`, `cardsMemory`, `routesMemory`, `detail.js foldMemory`, all through the one `common.js viewerMemory(name, values)`): never in the layout object, never exported.
- Scripts are inlined in this order, each in its own `<script>` block: `common.js`, `detail.js`, `universe.js`, `schema.js`, `print.js`, `flow.js`, `boot.js` (`print.js` passes through `page._inline` like a library, so no `</script` can close its block). Page-wide constants and pure helpers are globals declared in `common.js` (`PAGE`, `STRINGS`, `L`, `esc`, `num`, `plural`, `THEME`, `CONTRAST`, `paintDot`, `dotEdge`, `sidePanel`, `filterRow`, `fillSelect`, `crumbs`, `dismissable`, `detailDomains`, `labelOf`, `tableTip`, `tableDesc`, `trajectory`, `flowRanks`…, the Graphviz helpers); it only declares (no DOM work at load but `document.documentElement.lang`) and holds no `</script`. Stateful services built by `boot.js` (`LAYOUT`, `EXPORT`, `DOMAINS`, `openInDetail`, `openFlow`, `closeFlow`) are passed to `startDetail(DATA, LAYOUT, EXPORT, DOMAINS)` / `startUniverse` / `startFlow` as parameters. A view never declares a global (`schema.js` declares `S`, `LOOK`, `sheetModel`, `boxSize`, `scopeTables`, `sheetSvg` and `startSchema` at its top level, as `common.js` does: M9.5's `print.js` declares its own `PRINT`, `PT`, `printPlan`, `printDocument`, `startPrint`… at its top level and reads the same model and emitter, D-092, D-095).
- UI strings, in every supported language (`en`, `fr`, D-016), are written `{ en: {…}, fr: {…} }[PAGE.lang]`: page-wide strings (used by `boot.js`, or shown with the same text by both views) in `common.js` `STRINGS` / `L`, a view's own strings in the `T` at the top of its start function. A count's noun is a `[singular, plural]` pair shown through `plural(n, forms)` (French: 0 and 1 are singular).
- The page's words (M9.1, D-084): the internal words (trajectory, flow, route, constellation, kind, fold) stay in code, ids, config keys and localStorage keys; the page says Lineage, Lineage graph, dependency, domain or layer, Table kind, "Draw … inside their table" (a string table never holds the old words: `tests/unit/test_page.py`). A control that cannot act is disabled with a visible reason, never inert or silently hidden (D-085); popovers (Help, Layout) are native `<details>` closed by `common.js dismissable`.
- Text on a colour takes `CONTRAST.textOn(fill)`, text drawn in a colour `CONTRAST.ink(color, background)`, so it reaches 4.5:1 whatever the config's colours (D-037). A kind or domain colour drawn as a mark reaches 3:1 on `THEME.bg` (D-042): a filled area keeps its colour and gets an outline in `CONTRAST.edge` (canvas stroke, `dotEdge` for a Graphviz cell, `paintDot` for a page dot); a line, a border or a bar of 6 px or less is drawn in `CONTRAST.edge` itself; a colour that passes gets no outline, so its look is unchanged; the scripts draw with `THEME`, the copy of `page.css :root` `--bg` / `--fg` / `--muted` / `--surface` / `--accent` / `--accent-soft` (change both together). Every number shown goes through `num` (D-039). French strings write `\u00a0` before `:` and `\u202f` before `?` `!` `;`, as escapes, never as literal characters; a label and a value are joined with `L.colon` (D-039).
- Style: the bodies of `startDetail` / `startUniverse` / `startFlow` are indented; a helper with a block body is a `function` declaration, a one-expression helper or lambda an arrow `const`.
- Names, descriptions and config labels are untrusted: set them with `textContent` / `title` (filter rows through `filterRow`), or pass them through `common.js esc`, the one HTML escaper (`& < > " '`), before any `innerHTML`; text inside a Graphviz HTML-like label goes through `dotText` (`esc`, then every backslash doubled: Graphviz reads `\\`, `\N`, `\G`… there as escapes); DOT ids and strings go through `dotStr`.
- Page behaviour is tested in headless Chromium under `tests/browser/` (D-019), with the libraries served from `vendor/` and no network (D-022); `tests/unit/test_page.py` only checks the rendered markup.
- A library is added or upgraded in `page.LIBRARIES` only, then `tools/vendor_libraries.py` refreshes `vendor/`.
- Every zoom of the page is a d3 zoom attached with `common.js zoomOn` to an HTML element that fills the stage (`#d-graph`, `#f-graph`, `#u-canvas`, `#s-graph`, all `touch-action:none`), never to an `<svg>`: no second zoom library, no second gesture handler (D-045). The wheel zooms in every view except the Schema tab, where `zoomOn(…, {scroll: true})` makes it scroll and leaves ctrl+wheel and the pinch to zoom (D-093).
- Any `#d-graph`, `#f-graph` or `#s-graph` CSS rule that changes how a diagram looks adds its property to `common.js INLINE`, or the exported SVG will not look like the screen (focus outlines and cursors are never exported).
- The Schema tab saves nothing (no layout section, no localStorage key, D-092); its sheet is deterministic. Its boxes and relations are drawn with `LOOK` and `S` only, text widths are measured (`textW`), a name never leaves its box.
- Export controls stay in the toolbars, never inside `.canvas-box`: they must not be drawn into the image. **Print…** (`#s-print-btn`) likewise.
- The print document (M9.5, D-095, D-096) lives in `<div id="print-doc" hidden>` and its `@page` rule in `<style id="print-page">`, both the last children of `<body>`, filled on demand and emptied after printing. The only `@media print` block of `page.css` is scoped to `html.printing` (set by `print.js build` while a print runs): without that class a Ctrl+P prints the page as before. Every page of a print is one `<section class="pp">` of the paper's exact size holding one inline SVG in millimetres; the drawing is `sheetSvg(…, 'full', { k, ids: false })` (ids as `data-id`, they repeat on tiles). The print saves nothing and fetches nothing; every name goes through `esc` (in `sheetSvg`) or `fitText` / `esc` (in `print.js`). `PRINT.MAX_SIDE` (5,080 mm) is the PDF viewers' page limit, not Chromium's (measured: Chromium writes pages of 200 m).
